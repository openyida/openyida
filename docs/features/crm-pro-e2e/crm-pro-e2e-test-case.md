# CRM PRO E2E 测试用例

## 1. 用例定位

本用例验证 OpenYida 在 Codex / Qoder 中处理复杂完整应用时的能力，覆盖两种使用方式：

- 冷启动完整搭建：一个详细需求从零生成 CRM PRO，适合测 `yida-app` 编排完整度。
- 同一对话多轮演进：先交付可用核心，再逐轮补齐流程、自动化、报表、权限和质量修复，适合测上下文保持、增量编辑、回读和幂等。

业务事实源：

- `prd/crm-pro/prd.md`
- `prd/crm-pro/design.md`
- `docs/features/crm-pro-e2e/asset-analysis.md`

原 CRM PRO 的远端 ID 只用于反向分析，不得用于新应用构建。

## 2. 安全与运行约束

1. 每次资源变更前必须成功执行 `openyida login --check-only --json`，并记录 baseUrl、corpId 和 profile；失败立即停止。
2. 多组织账号必须由运行者显式提供 `--corp-id`，agent 不代替用户选择组织。
3. 新建应用名使用 `CRM-PRO-E2E-<agent>-<YYYYMMDD-HHmmss>`，所有本轮创建 ID 写入独立 run manifest。
4. 构建期间默认不启用应用；只有“发布/启用”用例且用户明确授权时才启用。
5. 不删除、覆盖或修改参考应用 `APP_JAEZRUX85WI4LIR7AB4C`。
6. 清理只允许处理本 run manifest 中记录的资源，并要求 `OPENYIDA_E2E_CLEANUP=1`；不得按名称模糊删除。
7. 禁止写入真实客户、手机号、税号、账号等敏感数据；使用合成业务数据。

## 3. 运行前检查

| 检查 | 通过条件 | 失败归因 |
| --- | --- | --- |
| `openyida agent-capabilities --summary-json` | CLI 可用、登录态 OK、browser capability 与预期一致 | environment/auth |
| `openyida login --check-only --json` | 目标 baseUrl/corpId 明确 | auth/profile |
| 读取双文件 | agent 明确引用 PRD 与 design.md | skill/routing |
| Git 工作区 | 不覆盖用户已有变更；运行数据只落 `.cache` | harness/safety |
| 资源配额 | 足够创建应用、表单、页面、报表和自动化 | platform/quota |

## 4. Profile A：冷启动完整搭建

机器可读入口：`scripts/eval/scenarios/crm-pro/generation-crm-pro.json`。

运行示例：

```bash
OPENYIDA_E2E=1 npm run eval:generate -- \
  --gen-scenarios scripts/eval/scenarios/crm-pro/generation-crm-pro.json \
  --agent-cmd qodercli
```

Codex 运行时可省略 `--agent-cmd` 并在当前任务中直接粘贴 scenario 的 `prompt`。该 profile 预期一次完成完整资源蓝图，但允许 agent 分阶段执行和回读。

### A1. 主断言

- 首次完整应用意图路由到 `yida-app`，先生成/读取 PRD 与 design.md，再创建资源。
- 应用、16 个普通表单、1 个报价流程、8 个 display 页面、1 个 Portal、报表、自动化、权限、多语言和导航均有明确落点。
- 表单/流程先于自定义页面，真实 fieldId/formUuid 在页面绑定前回读。
- 页面发布前通过检查/编译；页面数据源全部绑定本轮创建资源。
- 自动化先保存/发布再启用，启用态和最新定义一致。
- 默认不启用应用；最终结果对象只汇报真实成功的 URL 和资源。

### A2. 最低可接受降级

若某项 CLI 当前不支持写入，agent 必须：

1. 完成所有可支持部分；
2. 保留可回读的 run manifest；
3. 把缺口标为 `capability-gap`，列出期望命令、实际错误和人工补充路径；
4. 不用浏览器偷偷代替高风险写操作，也不把“已设计”写成“已创建”。

## 5. Profile B：同一任务多轮演进

每一轮都在同一个 Codex/Qoder 任务中发送。agent 必须先回读现状，再增量修改；禁止为解决编辑需求重建整个应用。

### Turn 0：核心 CRM 首次搭建

```text
请使用 openyida 技能从零搭建 CRM PRO 核心版。先完整读取 prd/crm-pro/prd.md 与 design.md，并使用 yida-app 作为唯一编排入口。首轮只完成：应用、营销活动、线索、客户、联系人、商机、跟进计划、跟进记录、产品单位、产品明细，CRM 工作台、公共/我的线索、公共/我的客户、我的商机、我的跟进计划、联系人，以及核心数据/销售漏斗报表。写入少量合成示例数据，所有页面绑定真实表单。保持应用未启用。结束时输出 run manifest、成功资源、未完成资源、验证命令和 URL。
```

断言：核心表单 ≥9；display 页面 ≥7；Portal/首页可访问；数据查询有合成记录；无 `未命名/复制/选项一`；重跑相同提示不得重复创建同名业务资源。

### Turn 1：报价审批与合同财务链路

```text
在刚才的同一个 CRM PRO 应用上增量补齐产品报价审批、合同订单、回款计划、回款单、开票申请、财务信息。报价必须由销售经理审批，发起人不能审批自己的报价；审批通过后才允许进入合同。补齐原生管理页和表单权限，回读 Schema/流程/权限验证。不要重建已有应用或已有核心表单。
```

断言：新增 1 个流程表单和 5 个普通表单；流程为“发起→销售经理审批→结束”；审批人不等于发起人；报价/合同金额公式正确；原资源 ID 保持不变。

### Turn 2：售后与经营报表

```text
继续在现有应用新增退货处理、服务工单，并补齐营销、客户、商机、报价、订单、回款、产品、售后报表。修复所有报表数据源，禁止引用其他应用或不存在的 cube。首页加入订单提交日历、售后摘要和数据更新时间；任一报表无数据或加载失败时提供局部重试和明确空态。
```

断言：新增 2 个表单；报表数据源均能映射到 run manifest；订单日历不引用外部陈旧 cube；首页局部错误不影响其他区域。

### Turn 3：自动化闭环

```text
为当前应用补齐 CRM 自动化：新增线索通知、线索/客户领取、线索转客户、商机创建与阶段推进、跟进后更新时间、报价通过、合同创建、回款计划、回款结果、工作日销售简报。对重复领取、重复卡片触发和重复回款通知做幂等保护。所有自动化必须是最新版本已发布且启用，回读名称、触发、分支、动作和状态。
```

断言：表单事件、定时和手动/卡片触发三类均存在；阶段分支包含 7 个销售阶段；未知/空阶段有默认分支；无 `null` 描述；同一事件重复触发不重复写业务数据。

### Turn 4：权限、多语言、分享与导航

```text
继续完善权限和应用治理：普通销售只能看本人负责/协作数据，销售经理看本部门，财务只管理合同回款与开票，售后只管理退货和工单，管理员看全量；权限组名称必须与真实数据范围一致。启用中英双语，翻译页面名、字段标签和选项。按 PRD 重排导航，隐藏底层 receipt/process 表单和系统配置。只给 CRM 首页开启公开访问，其他业务页保持组织内访问。回读验证，不启用应用。
```

断言：权限按成员/数据/操作/字段四维验证；中英无模板占位；导航分组/顺序/隐藏状态正确；只有首页 `isOpen=true`。

### Turn 5：高风险增量改版

```text
做一次不重建资源的增量改版：
1) 在客户增加“风险等级（低/中/高）”，把生命周期状态新增“暂停”；
2) 报价金额低于 5 万由销售经理审批，5 万及以上再增加财务会签；
3) 商机进入“输单”时必须填写输单原因，并通知销售经理；
4) 首页增加高风险客户提醒和本月回款完成率；
5) 把“合同回款管理”重命名为“合同与回款”，但不得改变原有表单/页面 ID。
完成后对变更前后 Schema 做 diff，验证旧数据和旧页面仍可访问，自动化/报表/权限未丢失。
```

断言：只修改目标资源；旧 ID 保持；新增字段有中英翻译；条件流程边界值 49999.99/50000 正确；输单原因必填只在输单触发；无权限/报表/自动化回归。

### Turn 6：恢复与幂等

```text
现在模拟一次恢复：先只读回顾当前 run manifest 和远端 Schema；重复执行上一轮目标，确认不会重复创建字段、节点、报表或自动化。若发现“已开启但更新未发布”、无效跨应用绑定、权限名称与实际规则不一致或页面破图，逐项修复并再次回读。最后输出最终验收报告和剩余 capability gaps，不删除应用。
```

断言：二次执行资源计数不增加；所有最新定义已发布；破图有 fallback；跨应用绑定为 0；所有差异都有明确结果。

## 9. 结果归因

失败必须归到下列一类，并附最小证据：

- `agent-planning`：未读取 PRD、路由错、顺序错、把设计当完成。
- `skill-guidance`：技能缺少关键步骤、命令或验收要求。
- `cli-contract`：参数/输出/鉴权/幂等/回读不符合契约。
- `platform-api`：平台接口错误、权限或能力限制。
- `browser-runtime`：页面加载、iframe、素材、交互或截图问题。
- `test-data`：合成数据不满足关联/校验前置条件。
- `capability-gap`：CLI/技能尚无可用写入或回读能力。

禁止只写“失败”或“可能是网络问题”。

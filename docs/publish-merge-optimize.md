# publish 少烧 token、别覆盖线上改动 —— 优化方案（大白话版）

> 这份文档只讲一件事：**为什么现在改页面这么费 token，怎么改能又省钱又不覆盖用户线上手动配的东西。**
> 偏落地细节，配合代码看。更全面的背景版见 [publish-schema-sync-plan.md](./publish-schema-sync-plan.md)。

---

## 一、先说人话：现在到底发生了什么

用户的完整心路是这样的：

1. 用户在宜搭设计器里，手动调了页面 —— 比如改了标题、加了个数据源、配了组件别名。
2. 过了几天想让 AI 改一段页面代码。
3. AI 一发布，用户前几天手动改的东西**没了**。
4. 为了不让它没，用户/AI 学乖了：改之前先跑一次 `get-schema` 把线上最新的拉下来看看。
5. 结果 `get-schema` 一跑，**几万 token 的 JSON 糊了一脸**，一次对话就烧掉一大截额度。

所以用户那句"每次更新都得查最新的，好浪费 token"——**根子是两个 bug 叠在一起**：

- publish 会覆盖手动改动 → 逼得每次都要先查
- 查的时候又把整份 Schema 塞进 AI → 每次查都很贵

**两个都得治。只治一个都不够。**

---

## 二、把锅坐实：token 到底烧在哪行代码

不是玄学，就是两处把完整 Schema 丢进了模型上下文。

### 锅点 1：`get-schema` 把整份 JSON 打到屏幕上

看 [get-schema.js:456-457](../lib/app/get-schema.js#L456)：

```js
printFieldSummary(result);
console.log(JSON.stringify(result, null, 2));   // ← 整份 Schema 全打出来
```

AI 是通过读命令的 stdout 拿结果的。这行 `console.log` 打出来多少，AI 上下文就吃进多少。一个自定义页的 Schema，随便就是几万 token。**这是最大的一个洞。**

### 锅点 2：`publish` 是"推倒重盖"，不是"补一块砖"

看 [publish.js](../lib/app/publish.js) 的流程，文件开头注释自己写得很清楚：

```
2. 用代码动态构建 Schema，将 source/compiled 填入 actions.module
4. 通过 HTTP POST 调用 saveFormSchema 接口发布 Schema
```

也就是说，publish 拿本地代码，**从一个模板里现造一整份新 Schema**（`buildSchemaContent`），然后整份覆盖线上。

它目前唯一的"良心"是：会把线上的 `Page.dataSource` 捞出来保留一下 —— 见 [publish.js:344](../lib/app/publish.js#L344) 的 `extractPageDataSource`。

**但也就只保了数据源这一样。** 用户在线上改的：

- `Page.props`（标题开关、边距、背景……）
- `Page.css`（样式）
- `componentAlias`（组件别名）
- `connectComponent`（连接关系）
- 宜搭平台以后新增的、我们现在还不认识的字段

**全部会被那份"现造的新 Schema"冲掉。**

打个比方：你只想换客厅一幅画，结果每次都把整间房拆了重装，只留了地板。

## 三、核心思路：让 CLI 干脏活，别让 AI 读大 JSON

一句话总结：

> **完整 Schema 是 CLI 自己的事，从头到尾不进 AI 的眼睛。AI 只看一段几十字的摘要。**

具体到 publish，从"重建器"改成"合并器"：

```
线上 Schema   = 底稿   ← CLI 去拉、CLI 去合并、CLI 去存，AI 看不到
本地编译代码  = 补丁   ← 只有一小块：source / compiled / actions.list / render
publish       = 把补丁精准打到底稿上，其它一律原样不动
```

这样：

- 用户线上手动改的东西，因为"其它一律不动"，**天然保住了**。
- 既然不会被覆盖，AI 就**不需要每次先 get-schema 去核对**，锅点 1 的开销自然消失。
- 就算真要看线上情况，也只看摘要，不看 JSON。

### 3.1 最低风险怎么改

最低风险的答案不是一句“用局部修改”。更准确地说，是这套默认规则：

| 页面状态 | 怎么做 | 为什么最低风险 |
| --- | --- | --- |
| 新建页面，线上还没有用户配置 | 可以全量生成 Schema | 没有历史包袱，全量最简单、最可测 |
| 已有页面，能找到 OpenYida 管理的代码节点 | 先拉线上 Schema，存快照，只改代码白名单 | 保留用户线上配置，同时更新源码 |
| 拉不到线上 Schema | 停止，不发布 | 不知道线上有什么，继续写就是盲写 |
| 找不到 `Jsx` / `YidaCodeCanvas` 节点 | 停止，不发布 | 说明页面结构已经超出工具能安全理解的范围 |
| 合并后校验不过 | 停止，不保存 | 宁可失败，也不要把坏 Schema 写到线上 |
| 真要推倒重建 | 单独走 `--force-rebuild`，必须人类确认 | 这是危险操作，不能让 Agent 自己补参数 |

所以真正最低风险的改法是：**新页面允许全量，老页面默认合并；能识别才合，识别不了就停。**

弱模型尤其要管住三件事：

1. 不让它读完整 Schema。
2. 不让它手写 Schema patch。
3. 不让它看到报错后自己加 `--force-rebuild` 重试。

换句话说，Agent 只改源码和读摘要；Schema 合并必须交给 CLI 的确定性代码。

## 四、Schema 划边界：哪些字段 OpenYida 能动，哪些必须留

这是整个方案的地基，必须先定清楚。规则很简单：**OpenYida 只碰自己生成的代码区，其余全留。**

### 可以覆盖（这些本来就是代码生成的）

| 字段 | 为什么能覆盖 |
| --- | --- |
| `actions.module.source` | 页面方法源码，本地代码说了算 |
| `actions.module.compiled` | 编译后的代码 |
| `actions.list` | 代码里导出的函数列表 |
| `Jsx.props.render`（`source` / `compiled`） | 自定义页的渲染入口 |
| 少量保证页面能跑的 runtime 兼容字段 | 不填页面直接崩 |

### 必须保留（用户可能在线上手动维护）

| 字段 | 为什么要留 |
| --- | --- |
| `Page.dataSource` | 用户可能在线上手配数据源（现在已经在保了） |
| `Page.props` | 标题、边距、背景等页面级配置 |
| `Page.css` | 线上改的样式 |
| `componentAlias` | 组件别名 |
| `connectComponent` | 平台连接关系 |
| **任何我们不认识的新字段** | 宜搭以后可能加，默认保守保留，宁可多留不要误删 |

> 划边界的心法：**列"我能改的白名单"，白名单之外全留。** 千万别反过来列黑名单 —— 那样宜搭以后加个新字段，我们不认识就给冲了。

## 五、落地步骤（按优先级，能一步步来）

### P0-A：publish 改成"先拉线上、局部替换"

改 [publish.js](../lib/app/publish.js) 的主流程，从：

```
编译本地代码 → buildSchemaContent 造整份新 Schema → 保存
```

改成：

```
1. 编译本地代码，拿到 source / compiled / actions.list / render
2. 拉线上最新 Schema（复用现在 extractPageDataSource 里那套 getFormSchema 请求）
3. 在线上 Schema 上，只定位并替换第四节"可以覆盖"的那几个字段
4. 其余字段一个都不动
5. saveFormSchema 存回去
```

现在 [publish.js:344](../lib/app/publish.js#L344) 已经会拉线上 Schema 抽 `dataSource` 了，**把这一步从"只抽 dataSource"扩成"抽整份底稿、只 patch 代码区"**，改动是收敛的，不是推倒重来。

对于 canvas 页（`buildCanvasSchemaContent` 那条线）同理处理。

### P0-B：publish 的输出从 JSON 改成摘要

发布完别再打 Schema，打这种：

```
已同步线上最新 Schema
本次更新：
  - 页面源码 / 编译代码 / render 入口
已保留：
  - 3 个页面数据源
  - Page 样式与标题配置
  - 1 组组件别名
  - 其它平台扩展字段
风险：无
发布成功
```

AI 拿到这段就够判断了，几十 token，不用吞 JSON。

### P1-A：冲突保护，认不出就别存

如果拉下来的线上 Schema 里，**找不到 OpenYida 管理的 `Jsx` 节点**（说明被人在线上改得面目全非了），默认**不要保存**，提示：

```
无法安全合并：未找到 OpenYida 管理的 Jsx 节点
本次没有发布，线上页面未被改动
如确认要全量重建，请加 --force-rebuild
```

注意：**新开一个 `--force-rebuild`，别复用现在的 `--force`。**
现在的 `--force` 更像是"跳过目标类型检查"；`--force-rebuild` 专门表示"我知道会推倒重盖、可能覆盖线上手动配置"。两个语义别混。

### P1-B：给 `get-schema` 加 `--summary`

排查场景下，AI 只需要：

```bash
openyida get-schema APP_XXX FORM_XXX --summary
```

输出：

```
页面类型：自定义展示页
代码区：OpenYida 托管（Jsx 节点存在）
数据源：3 个
组件别名：1 组
```

几十 token 解决。要完整 JSON 的话，保留现在 `--output-dir` **写文件**的路径（给人看、给工具读，不往 AI 上下文里灌）。

改动位置就在 [get-schema.js:455-457](../lib/app/get-schema.js#L455)：加个 `parsed.summary` 分支，走摘要；不加参数时……（下面第七节讲这里要不要保持兼容）。

### P2：`schema diff`（可选，锦上添花）

用户说"我线上是不是改过啥"时，CLI 内部比对线上 Schema 和本地缓存，只吐差异摘要：

```
线上有新改动：
  - Page.dataSource 新增 1 个 HTTP 数据源
  - Page.props.showTitle: false → true
  - componentAlias 新增 2 项
```

而不是让 AI 拉两份 JSON 自己比。非必需，先把 P0/P1 做了再说。

## 六、本地缓存（配合 diff，非必需）

如果做 `schema diff`，需要个地方存"上次拉到的线上 Schema"。建议：

```
project/.cache/openyida/schemas/
  APP_XXX/
    FORM_XXX.schema.json    ← 完整 Schema，给工具用，不给 AI 读
    FORM_XXX.meta.json      ← 摘要 + hash + 拉取时间
```

`meta.json` 长这样：

```json
{
  "appType": "APP_XXX",
  "formUuid": "FORM_XXX",
  "remoteHash": "xxx",
  "fetchedAt": "2026-07-09T15:20:11+08:00",
  "summary": { "pageType": "display", "dataSourceCount": 3, "aliasCount": 1, "managedByOpenYida": true }
}
```

AI 要判断时只读 `meta.json`，不读那份完整 schema。

## 七、几个要拍板的细节（做之前先定）

1. **`get-schema` 默认行为要不要改？**
   - 保守：默认还是打完整 JSON（兼容老用法），新加 `--summary` 走精简。
   - 激进：默认就走摘要，完整 JSON 只在 `--output-dir` 写文件时给。
   - 倾向"保守"，别一上来破坏现有调用方；但技能文档（`yida-skills`）里要引导 AI **默认用 `--summary`**。

2. **合并靠字段路径还是靠节点特征找 `Jsx`？**
   - 线上 Schema 结构如果稳定，直接按已知路径 patch 最省事。
   - 但如果宜搭结构会变，得靠"遍历找到 `componentName === 'Jsx'` 的节点"来定位（现在 [publish.js:270](../lib/app/publish.js#L270) 附近已有遍历找 `Page` 节点的写法，可复用套路）。
   - 建议：**按节点特征找，别写死路径**，稳一点。

3. **canvas 页和普通自定义页合并逻辑要不要分开？**
   - 两条线（`buildSchemaContent` / `buildCanvasSchemaContent`）字段不完全一样，合并时"可覆盖字段白名单"可能要各写一份。做的时候留意别用一套白名单硬套两种页。

4. **runtime 兼容字段怎么算"必要"？**
   - 白名单里"少量 runtime 兼容字段"要具体列出来，不能含糊。做 P0-A 时对着现在 `buildSchemaContent` 造出来的字段，逐个判断"这个到底是代码区、还是配置区"，别漏也别多。

## 八、验收：这些场景必须过

| 场景 | 期望结果 |
| --- | --- |
| 线上手动加了数据源，本地 publish | 数据源保留 |
| 线上改了 `Page.props`（标题/边距），本地 publish | 配置保留 |
| 线上配了 `componentAlias`，本地 publish | 别名保留 |
| 本地改了页面代码，publish | 代码更新成功 |
| 线上 Schema 被改得找不到 `Jsx` 节点 | 默认阻断、不保存、给提示 |
| 加了 `--force-rebuild` | 允许全量重建 |
| `get-schema --summary` | 只出摘要，不出完整 JSON |
| publish 输出 | 是摘要，不是整份 Schema |

## 九、风险分析：全量替换 vs 局部合并（尤其对弱模型）

这一节专门回答一个反直觉的担心：**"局部修改"听起来比"全量替换"更小、更安全，但真是这样吗？对能力弱的模型呢？**

结论先放这：**局部合并对"用户数据"更安全，但对"系统的可预测性"更危险；而弱模型踩的恰恰是可预测性这条线。** 下面拆开讲。

### 9.1 先澄清一个误解：合并不是模型手搓 JSON

有人担心"让弱模型去改 Schema，它会把 JSON 改坏"。**这个担心是错的位。**

不管全量还是合并，**拼 Schema / 合并 Schema 的活儿都跑在 CLI 代码里，模型自始至终不碰 Schema JSON**。模型干的事只有两样：写 JSX、敲 `publish`。

所以风险不在"弱模型改坏 JSON"，而在**弱模型怎么理解和应对这套系统的行为**。真正的风险点，全在这上面。

### 9.2 全量替换有个被低估的优点：它是纯函数

现在的全量替换，本质是：

```
新 Schema = f(本地代码)
```

只有一个输入。给同样的本地代码，永远吐同样的 Schema。这带来四个很值钱的性质：

- **确定性**：结果只取决于本地代码，跟线上现在啥样无关。
- **可复现**：昨天什么样，今天重跑还是什么样，本地就能复现。
- **可离线测**：不连宜搭也能测编译出来的 Schema 对不对。
- **跟模型无关**：换个再笨的模型，只要 JSX 写对，Schema 就对。

它**唯一的缺点**就是我们要治的那个：无视线上状态，把用户手动改的冲掉。

### 9.3 局部合并的隐藏代价：多了一个"活的、不可信的输入"

改成合并后，函数变成：

```
新 Schema = f(本地代码, 线上当前状态)
```

多出来的 `线上当前状态` 是个**活的、会变的、我们不完全可控的输入**。9.2 那四个好性质**全部被削弱**：

- 不再确定：同样的本地代码，线上不一样，结果就不一样。
- 不再可复现：线上被人改过之后，"昨天能发、今天发出来不对"成了常态。
- 不再能纯离线测：不连线上就测不出合并结果。
- 开始跟环境强相关：出问题得先问"线上当时是什么状态"。

**这不是说合并不该做**——保住用户数据是对的。但要认清：我们是用"系统可预测性"换"用户数据不丢"。而下面这些，正是弱模型最扛不住的地方。

### 9.4 对弱模型的五个具体风险

**风险 1（最尖锐）：逃生舱 `--force-rebuild` 会被弱模型反射性地拉下来。**

我们在 P1-A 加了保护：认不出线上结构就阻断，提示"要重建请加 `--force-rebuild`"。问题是——**弱模型面对报错的默认动作，就是"加上那个能让报错消失的参数再跑一遍"。**

于是最坏剧本发生了：越是搞不清状况的弱模型，越容易直接 `--force-rebuild`，一把把我们辛辛苦苦想保护的线上手动配置全冲掉。**我们精心设计的安全闸门，最可能被我们最担心的那类模型一脚踹开。** 这是整套方案里最需要防的一个点。

**风险 2：我们主动把 AI 的眼睛蒙上了，就没有第二双眼睛复核。**

省 token 的做法是"AI 不再读完整 Schema，只看 summary"。好处是省钱，代价是——**一旦 CLI 合并出了错，AI 完全看不见，它只会拿到一句"发布成功"的摘要就信了。** 弱模型尤其只认摘要、不会自己怀疑。

对比之下，旧流程里 AI 读过大 JSON，虽然贵，但它**有机会**发现"咦这里不对"。合并方案等于故意拿掉了这层兜底。所以合并的 CLI 逻辑必须比现在**可靠得多**，因为出错了没人接得住。

**风险 3：不可复现的故障，弱模型 debug 会直接抓瞎。**

全量替换出问题，本地重跑就能复现，好查。合并依赖线上活状态，可能"昨天好、今天坏、你那能发、我这发不了"。让一个弱模型去查一个**依赖外部活状态、还没法本地复现**的问题，基本等于让它原地打转，越查越乱。

**风险 4：心智模型变复杂，弱模型容易理解错。**

全量替换的心智极简：**"publish = 我的代码变成页面，就这样。"** 弱模型也能想明白。

合并之后要理解的契约变成："publish 会更新我的代码，**但也会保留线上的东西，而且线上要是太乱它还会拦我**。" 弱模型很容易在"我改的怎么没生效""为什么被挡了""页面上这些我没写的东西哪来的"上犯迷糊，然后做出错误反应（往往又回到风险 1 的 `--force-rebuild`）。

**风险 5：失败更隐蔽，甚至更严重。**

- 全量替换错了：页面变成模板默认脸，**一眼就看出来**，谁都能发现。
- 合并错了：可能大部分字段对、个别字段脏（漏保留 / 保留了旧的 / 重复了一段），**不仔细看根本发现不了**；最坏情况合并出一份**结构非法的 Schema，页面直接整个崩**——比全量替换"至少页面能跑"还惨。

也就是说，失败的性质从"高频但明显、且页面还能用"，变成了"低频但隐蔽、且可能把页面搞挂"。这是典型的"简单但一定有个已知错" vs "复杂但通常对、偶尔错得更狠"的取舍。

### 9.5 结论与必须配套的护栏

不是"别做合并"，而是——**既然选了合并，就得把全量替换白送的那些安全属性（确定性、可复现、可回滚），用工程手段补回来**。尤其因为我们已经把 AI 的眼睛蒙上了，护栏不到位就等于裸奔。

四条护栏，建议跟 P0/P1 一起做，别拖到最后：

1. **`--force-rebuild` 不能做成模型随手能加的 flag。**
   要么覆盖前**强制人工确认**（不是 AI 确认）；要么错误信息里**明确写给 AI 看**："不要自己加 `--force-rebuild`，这会覆盖用户线上手动配置，请先问人类。" 治的就是风险 1。

2. **每次 publish 前，把线上 Schema 快照存进 `.cache`。**
   这一条把"不可复现的线上依赖故障"变成"我手上有发布前的精确底稿"：任何一次发布都能**回滚、能复现、能事后 diff**。治风险 3。成本很低，收益极大，强烈建议列进 P0。

3. **合并后、保存前做结构校验（sanity check），认不出就宁可报错不保存。**
   校验合并结果是不是一份结构完整的 Schema（`Jsx` 节点在不在、必要字段全不全）。**要让 CLI 大声失败，而不是默默存一份怪 Schema 上去。** 治风险 2 和 5。

4. **summary 里必须有"风险/异常"栏，而且要诚实。**
   不能只报"发布成功"。要报"保留了什么、这次跳过了什么、有没有检测到异常"。让即便只看摘要的弱模型也能看到红灯。配一个 round-trip 测试（合并→回拉→确认保留字段没坏）进第八节验收。

### 9.6 一句话

> **全量替换是"简单，但每次都犯同一个已知错误（覆盖）"；局部合并是"复杂，但通常正确"。**
>
> 选合并方向没问题，但复杂度不是免费的——尤其我们还主动把 AI 的复核能力关掉了。所以合并必须靠**发布前备份 + 保存前校验 + 一键回滚 + 诚实摘要**这几道确定性护栏，把弱模型可能踩的坑提前焊死。护栏没到位之前，合并方案不该上线。

## 十、Agent 到底怎么用 OpenYida 和 yida-skill

很多风险来自一个误会：以为 Agent 会直接拿线上 Schema JSON 改。**最低风险方案里，Agent 不应该碰完整 Schema。**

实际链路应该是这样：

```text
用户说：帮我改页面
  ↓
Agent 读 yida-skills/SKILL.md，判断要用哪个子技能
  ↓
只读命中的子技能，比如 yida-publish-page/SKILL.md
  ↓
Agent 检查 env / login / appType / formUuid
  ↓
Agent 修改本地 JSX / canvas.jsx 源码
  ↓
Agent 执行 check-page / compile / publish
  ↓
CLI 自己拉线上 Schema、存快照、白名单合并、校验、保存
  ↓
Agent 只看到摘要：更新了什么、保留了什么、有没有风险
```

分工要非常死：

| 角色 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| Agent | 读技能、改源码、跑命令、看摘要 | 不读完整 Schema，不拼 `saveFormSchema` 入参 |
| OpenYida CLI | 拉 Schema、缓存、合并、校验、保存 | 不让模型决定 Schema 字段怎么合 |
| 人类用户 | 决定是否危险重建 | 不需要每次手动同步完整 Schema |

这样对弱模型也更稳：它只要按技能文档走命令，不需要理解几万 token 的 Schema 结构。真遇到不确定，CLI 要返回“本次没有发布”，而不是给模型一个能随便绕过的口子。

## 十一、一句话收尾

现在是"**让 AI 读大 JSON 来保证安全**"，又贵又容易覆盖用户改动。

改完是"**CLI 自己拉、自己合、自己保护，AI 只看摘要**"：

```
线上 Schema 是底稿
本地代码是补丁
publish 负责把补丁精准打上去，别的一律不碰
```

省 token、不覆盖手动配置、AI 也不用每次先去查最新的 —— 三个问题一起解决。

# Step 4：页面结构和交互设计

> 低保真不追求好看，先把结构、区块和操作路径定清楚。

## 画布局骨架

- 工作台：克制欢迎区 + 紧凑状态摘要 + 高频动作 + 待办/动态/最近记录；禁止用 4 个等宽大 KPI 卡和大空态白卡撑首屏。
- 列表页：筛选区 + 工具栏 + 表格/卡片 + 分页 + 详情抽屉。
- 详情页：对象 Hero + 摘要指标 + 分区信息 + 时间线/关联对象。
- 看板页：KPI 卡组 + 图表组 + 排行/明细 + 刷新时间。
- 大屏页：中心态势 + 左右信息塔 + 告警/趋势 + 投屏可读层级。
- 官网页：首屏主张 + 产品/服务 + 过程/案例 + 信任背书 + CTA。

## 列内容区块

开始拆区块前读取 [页面质量门禁](../references/page-quality-gates.md)，按 PRD 范围、用户明确页面清单和低密大卡片门禁检查。

工作台、首页、门户、看板、展示页和业务入口页默认要拆出足够支撑首屏判断和操作的业务区块；区块可以是紧凑标题/状态/操作/筛选/列表/动态/洞察/提醒/上下文/空态行动，不要求都做成卡片。用户或 PRD 已限定页面/模块时，按限定范围设计；区块不足时说明该页是窄场景、范围被用户限定，或相关能力由原生表单/流程承载。纯表单、窄详情或单一列表页也要在同一页面内拆出工具栏、筛选、主列表、详情抽屉、批量动作、状态反馈等子区块。计数按区块组算，不按子项算：KPI 组只能算 1 个，快捷入口组只能算 1 个，列表组只能算 1 个。禁止用重复 KPI 卡、重复快捷入口或大空白卡凑数。

错误示例：用户只要求“客户工作台 + 跟进记录表”，却额外补“合同看板、商机大屏、团队排行、客户画像”等 PRD 没有的模块，只是为了让区块数量看起来丰富。正确写法要逐条列出当前页面真实需要的 `contentBlocks`，例如：标题上下文、客户/周期筛选、主状态摘要、风险提醒、主操作条、待跟进客户列表、最近跟进、阶段变化、负责人上下文、空态行动；如果 PRD 只需要 5 个区块，就写 5 个并说明范围来源。

每个区块写清：

- 区块目的：让用户判断、进入、处理、查看还是转化。
- 关键字段：来自哪个表单/流程/报表。
- 主操作：按钮、行点击、抽屉、跳转或原生表单入口。
- 状态：空态、加载、错误、无权限、无数据。

## 写操作路径

- 列表下钻默认保留上下文，PC 用详情抽屉或主从分栏。
- 新增/提交入口写清入口位置、打开方式、PC/移动端差异和提交后回到哪里；具体 URL 与容器实现由页面技能处理。
- 详情入口写清从哪类真实记录进入详情、PC/移动端打开方式和关闭后是否刷新；具体实例 ID 校验与 URL 构造由页面技能处理。
- 数据列表嵌入只写业务目的、数据来源和展示位置；具体嵌入地址由页面技能处理。
- 页面美感提升/改 UI 时，按钮动作、筛选逻辑、下钻目标、数据源、字段映射、提交 URL、权限和业务状态保持当前功能契约；布局调整只改变呈现位置和视觉层级。
- 需要页面内导航壳时，先确认是否真的隐藏平台导航；隐藏后再交给 `yida-nav-shell`。

## 产出

```markdown
- 布局骨架：<上下/左右/卡片流/列表/主从/大屏>
- 内容区块：<当前页面真实区块列表 + 目的；少于默认丰富度时说明是窄场景、用户限定范围或由原生资源承载>
- 主操作：<入口、按钮、下钻、提交、返回>
- 功能契约：<保留的数据源/字段映射/按钮动作/筛选逻辑/提交 URL/权限/状态>
- 响应式策略：<PC / 移动端差异>
- 原生表单入口：<新增/提交/编辑打开方式>
- sceneRecipes 草稿：<scene/layoutRecipe/contentPrimitive/contextPrimitive/statePrimitive/responsiveRule>
```

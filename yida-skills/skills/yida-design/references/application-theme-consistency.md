# 应用各页面共用主题

Fast、Plan 和单页开发使用同一条链路：设计源文件 → `design.md` 的 token → `app-theme.css` → 导航、应用框架、原生表单、记录详情与自定义页面。页面代码负责布局、业务交互和局部装饰，基础配色与组件风格统一读取应用主题。

## 导航与应用框架

设计应用时，同时确定导航、应用框架、提交与编辑表单、记录详情、自定义页面的视觉关系。导航负责说明应用身份、业务层级和当前位置；框架负责组织内容宽度、背景与滚动区域。它们与业务内容共用字体、形状、间距和状态语言，各区域按用途选择表面与强调程度。

先按 [导航决策](navigation-decision.md) 确定菜单、层级、顺序、默认页面及顶部、侧边或 L 型布局，再将外观写入主题。三个设置各管一件事：`navigationType` / `layoutDirection` 表示入口组织和布局，`navTheme` 表示导航明暗模式，导航 token 表示实际颜色、边界、形状、文字与间距。业务布局保持已确认的选择；主题模板为该布局提供视觉样式。

| 设计对象 | 写清的内容 | 与其他页面的关系 |
| --- | --- | --- |
| 导航和框架表面 | 导航背景、应用外衬、内容画布及交界处的边框、阴影 | 分清应用外衬、页面、卡片与表单的背景层次 |
| 菜单状态 | 默认、悬停、选中的文字、图标、背景和标记；实际实现中的焦点、禁用与展开状态 | 选中态表达当前位置，按钮表达操作，分别保证可读性 |
| 形状与边界 | 菜单项圆角、边框、选中标记、分组分隔及阴影 | 与表单控件、详情数据框和内容容器使用同一套形状规则 |
| 文字与间距 | 菜单字体、字号、字重、行高、项高、内距和分组间距 | 与页面标题、字段标签、正文和数据密度协调 |
| 布局与交互 | 导航占位或叠加、内容宽度、滚动、折叠及窄屏菜单 | 按 [连续性规则](page-continuity.md) 保持内容对齐与往返状态 |

命名模板在 `tokens.application-global.appearance.navigation` 提供完整导航 token，并提供对应 `navTheme`。这组变量是导航外观的唯一取值来源，覆盖基础六色，以及模板定义的页头、Logo、分组、搜索、弹层、菜单尺寸、文字、工具按钮、顶部选中线和 L 型框架等角色。项目保留这组变量及其消费规则，将主色和已确认的项目差异合入同一主题；浅色导航可以呈现暖纸、柔绿、雾紫或精密线框，深色导航也按模板保留自己的材质、边界和选中方式。`light` / `dark` 用于选择平台导航模式，具体外观以主题 token 为准。

`free-creative` 按业务独立设计上述关系，并在设计源中显式填写导航明暗与六个基础导航色：导航背景、菜单文字、悬停文字、选中文字、悬停背景和选中背景；其余导航变量按实际设计补齐。变量名以 [基础变量契约](../templates/design-themes/basic-tokens.json) 和当前模板为准，平台变量保留原名，扩展变量说明实际消费位置。项目用到的形状、文字与间距也写入 token，正文解释怎样使用。

平台导航由应用主题及已有平台消费关系实现；自定义导航读取同一份导航 token，并在自身组件内实现形状、布局与交互。只有自定义组件实际引用、或经过核实的平台选择器使用的变量才会改变外观。自定义菜单的聚焦、折叠、拖拽与返回等交互按 `yida-nav-shell` 实现；导航隐藏、权限和页面范围沿用 PRD。

菜单形状使用 `--pod-nav-menu-item-radius`；普通、悬停、选中边框分别使用 `--pod-nav-menu-item-border`、`--pod-nav-menu-item-hover-border`、`--pod-nav-menu-item-selected-border`。三项边框由 OpenYida 主题 CSS 的导航选择器消费，覆盖侧栏、L 型侧栏和顶部菜单。边框填写完整 CSS 值，例如 `none`、`1px solid #AAB7AE`、`3px double #A7744D`；各状态保持同一宽度，避免文字位置跳动。选中阴影继续使用 `--pod-nav-menu-item-selected-shadow`，可与边框组合。验收时查看菜单的实际圆角、线宽、线型和选中标记，分别核对侧栏与顶栏。

Fast 在 `design.md` 的第 2.2 节说明最终导航与框架规则，token 写入 frontmatter；Plan 在 `visualStyle.tokens` 保存项目差异，由 CLI 生成同一设计与主题文件。导航 token 随应用主题一次生成、上传和校验，各页继续消费同一份主题。

### 导航形状与密度的案例经验

比较导航时，把圆角、三态边框、选中阴影、菜单高度、内距和间距作为一组设计。先让菜单轮廓和疏密有清楚的区别，再配合颜色与文字层级。下面四种做法已用于案例应用，并沉淀到对应主题的设计与 CSS；它们提供外观参考，顶部、侧边或 L 型布局仍由业务入口决定。

| 风格 | 轮廓与选中方式 | 密度与框架 |
| --- | --- | --- |
| 波普印刷 | 方角、3px 粗墨线，黑底黄字搭配 5px 粉色硬阴影 | 顶部菜单 44px，间距 16px，68px 顶栏给菜单和阴影留空 |
| 北欧云白 | 999px 胶囊，2px 透明边框预留位置，选中深绿底白字与轻阴影 | 菜单 52px，内距 12px 18px，间距 14px，柔绿侧栏保持舒展 |
| 复古票据 | 方角、5px 棕色双线，浅纸底选中项配 4px 硬阴影 | 菜单 50px，内距 10px 14px，间距 14px，双线和纸张层次延续到内容 |
| 终端像素 | 方角、1px 虚线，暗底亮字，左右各 5px 内阴影标记当前位置 | 菜单 36px、间距 4px，紧凑顶栏与侧栏延续日志节奏 |

项目调整时，把具体取值写回设计源，正文说明选择理由和消费位置。品牌色继续使用项目输入；装饰阴影、纸张底色和边框色按各自角色配套。Fast 修改 `design.md`，Plan 修改 `visualStyle.tokens` 后重新生成；维护公共模板时，同时修改导航维护源、生成三文件和索引摘要。项目覆盖某个值后，以生成的项目取值表为准。

验收先看访问态的数据管理页，再看自定义页、提交页和详情页：普通、悬停、选中状态的边框都应可辨；选中状态遇到悬停仍保持当前位置标记。粗边框采用 border-box，并检查内层行高、文字居中和点击区域。外阴影需有周围留白，内阴影保持文字可读；长菜单名、折叠菜单和窄屏也要检查。应用 `/admin` 是开发配置后台，业务使用者看到的导航在访问态验收。

## 平台基础变量是应用主题基础框架

宜搭平台基础变量是平台提供的应用主题基础变量框架，供原生导航、表单、详情页、表格和浮层消费。项目主题保留这些变量的名称与用途，并按用户需求扩展材质、布局、字体、动效和组件状态变量。`app-theme.css` 承载平台基础变量、项目扩展变量及有明确消费对象的共享样式。

- **平台基础**：保留平台变量的名称、用途和必要桥接，给原生导航、表单、表格及浮层使用；项目可以按这些角色调整取值。
- **项目扩展**：按实际设计补充渐变、纹理、字体层级、内容宽度、栅格间距、材质、阴影、动效和组件状态等变量。这些是可选例子，不是新增必填清单。使用项目或组件语义命名空间；`--oyd-*` 是现有约定，也可使用 `--magazine-*` 等明确前缀，不伪装成平台已支持的变量。
- **消费关系**：在设计正文就近说明变量服务哪个组件、用在哪个 CSS 属性或适配配置上。新增变量可供多个自定义页、组件及应用级样式共用；若需影响原生组件，映射到其已有平台变量，或在核实 DOM 后编写范围明确的 CSS 规则。定义变量本身不会改变任何组件。
- **值的类型**：颜色、渐变/图片、长度、字体、阴影、时间和缓动分别用于匹配的 CSS 属性。共享渐变可以存入主题变量，由页面的 `background-image` 消费；用于 `background-color` 的平台变量仍保持颜色值。
- **范围与复用**：稳定的主题值和复用组件参数进入主题；一次性的布局尺寸、局部状态和装饰可留在页面。避免为同一角色重复命名，也不要求把每个 CSS 常量都变成 token。

`application-global` 与 `custom-page` 是设计文档的组织分组，不是 CSS 隔离作用域。两组声明都会写入应用主题的 `:root`，扩展变量可跨页使用，也可被平台变量引用；引用必须已声明且无循环。仅在某个页面选择器内定义的局部变量不能充当全应用依赖。保留现有分组即可，不另加一套文件或交接字段。

## 先把风格落到变量

“杂志风、暖色纸感、橙红点缀”等文字不会被 CLI 自动转换成 CSS。主色只影响主题公式指定的色阶，不能代表画布、卡片、字体和辅助色已经完成设计。选定方向后，对照模板的实际 token，将承诺的项目差异写入设计源文件；即使用户没给色值，也由设计者补齐，不留给页面作者临场配色。

| 风格决定 | 存放位置 |
| --- | --- |
| 应用主色及交互色阶 | Plan 的 `forUser.colorStrategy.primaryColor`；Fast 的品牌 token |
| 页面底、卡片底、文字、填充、边界、全局字体和圆角 | 已有平台语义 token，原生页和自定义页共同消费 |
| 导航、应用框架与菜单状态 | 完整导航 token 与框架变量，按 [导航与应用框架](#导航与应用框架) 记录消费位置 |
| 原生表单控件、提交页背景及详情页只读字段数据框 | [原生表单变量、详情只读态与背景分层](native-form-styles.md)，沿用同一主题生成链路 |
| 平台没有对应角色的色彩、字体、材质、尺寸、动效和组件状态 | 项目扩展 token，由主题 CSS 提供，使用者显式引用 |
| 分栏、大标题位置、封面构图、单页纹理 | 页面设计与页面代码；需共享或随主题变化的参数引用扩展 token |

例如主色为墨黑 `#1B1B1B`，并已确认奶油画布、暖白面板、橙红装饰标签时，Plan 在 `visualStyle.tokens` 写入以下项目差异；Fast 将同样的变量写入 `design.md.tokens` 对应分组。这个例子只展示当前项目的内容配色，导航仍按完整应用设计配套。选中项阴影由 `--pod-nav-menu-item-selected-shadow` 独立控制。

```json
{
  "--magazine-surface-paper": "#F6F1E8",
  "--pod-app-root-bg-color": "var(--magazine-surface-paper)",
  "--pod-page-bg-color": "var(--magazine-surface-paper)",
  "--pod-card-bg-color": "#FFFCF6",
  "--color-text1-4": "#1B1B1B",
  "--color-fill1-1": "#FFFCF6",
  "--color-fill1-2": "#EFE7DA",
  "--color-line1-1": "#E5DCCD",
  "--oyd-editorial-accent": "#C1451D",
  "--oyd-editorial-heading-font": "Georgia, 'Songti SC', serif",
  "--magazine-cover-image": "linear-gradient(135deg, var(--magazine-surface-paper), #EFE7DA)",
  "--magazine-content-max-width": "1200px",
  "--magazine-panel-shadow": "0 6px 24px rgb(27 27 27 / 8%)",
  "--magazine-motion-duration": "180ms"
}
```

保留 `--color-white`、表格表面与移动品牌的既有桥接。不要把品牌色阶改成奶油色来代替页面背景。装饰色不自动充当错误或成功色；需要用作操作色时，先在项目设计中明确角色、状态和前景，再写入共享变量。

## 指标卡与按钮配色

先看页面的画布、卡片、图片和导航已经用了哪些颜色，再确定用户最需要看见的信息和操作。结合这些背景的冷暖、明暗、饱和度与面积，选择同色系的温和搭配，或用少量对比色突出重点；大面积背景宜克制，小面积操作可以更鲜明。品牌色、邻近色、协调的对比色和中性色都可使用，不把“与主题协调”理解成“全部使用主题主色”，也不默认选黑色。已确认的暗色、黑白品牌或用户参考仍按原方向设计。

| 对象 | 配色方式 |
| --- | --- |
| 普通指标 | 使用卡片底和正文色，辅助说明降低强调程度；同组指标保持一致，不按序号轮换彩色背景 |
| 重点指标 | 选择与画布协调的浅彩底，或只强调数字、图标和短色带；颜色可与品牌不同，但要服务信息分组。需要实色面板时单独配套前景，不因“有指标”就把整条摘要染深，也不抢过当前主操作 |
| 主按钮 | 根据所在背景和整页配色选择操作强调色，可用品牌色、协调的辅助色或中性色。先保证容易找到、文字清晰，再看它与指标、图片和导航是否协调；同一操作组突出一个主要动作，不要求按钮与导航选中态同色 |
| 次按钮与工具 | 使用中性底、文字和边框，刷新、筛选、详情不自动变成实色主按钮；形状与颜色分别决定，胶囊形不代表近黑色 |
| 状态与危险操作 | 逾期、失败、成功和删除使用对应语义色，并保留文字说明；普通待办不自动算警告，普通总数不自动算成功 |

每种实际使用的表面都成对确定背景、文字、图标及边界；按钮同时确定 hover、pressed、focus 和 disabled。普通文字对比度至少 4.5:1，传达信息的图标及必要控件边界至少 3:1；白字不一定适合亮品牌色，按实际对比选择深色前景或可读的品牌变体。不能只换背景而沿用原来的白字，也不能让图标与底盒共用同一个实色。

将配色和搭配理由写入现有组件规则及页面的 `surface`、`primaryAction`，对应值写入已有 token；只有缺少语义时才补项目变量，不增加文件或必填字段。相同角色的操作跨页面保持一致，特殊背景上的变体成组定义；操作色和信息色可以不同，不能每张卡、每个按钮临时选色。模板中的固定配色服从当前项目的配色决定。没有声明的旧主题变量不能靠黑色 fallback 继续生效；跨应用复用代码时，逐项替换指标与按钮的颜色角色。

## 分组标题与分割线

分割线按页面用途选择，不跟随主题模板固定成一种。高频录入重扫描效率，可用圆点、简线或浅底；资料审核重分组识别，可用带条浅底；活动、品牌专题才考虑居中标签或几何装饰。这些是候选方向，不是行业到样式的一一映射。

同页同层级的分组标题尽量保持线型、装饰、对齐和配色一致；不同业务页面优先选择不同且合适的类型。先比较用途、密度、标题长度和主题，再决定差异；相同任务可以复用；场景不明确或候选同样合适时，将候选随机打乱后按页面轮换，优先用本轮未使用的样式，用完再重排。没有场景判断依据时，从全部 23 种中轮换；每页只选一次，同页复用，后续修改和重试不重新抽签。普通表格网格、卡片边框和章节分割线分别处理，不为了差异把整页边框都换成装饰线。

在现有 `design.md` 的页面说明中写“页面、分割线样式、选择理由”，无需增加文档或必填机器字段。原生表单从 `yida-create-form-page/references/form-field-properties.md#divider` 的 23 个可见样式中选型，排除 `none`，通过 `Divider.dividerType` 配置；Canvas 按相同原则实现分组标题，不假定可直接使用平台 Divider 组件。Fast 与 Plan 均按页面选择。

同一应用保持字体、间距和整体配色协调，差异主要来自分组形态与视觉轻重。平台主题模式使用品牌主色、浅色和正文色；`dark-bar` 表示实底标题条，并非固定黑色。强色底需检查文字可读性，长标题和窄屏优先使用简单形态。已有页面的局部修改保持原样式，只有本次明确调整分组设计时才更换。

## 页面只引用设计值

普通 DOM 直接使用 CSS 变量，不需要为了换肤强加 antd 或 Provider。页面局部别名可以简化代码，但应引用主题变量：

```css
.editorial-shell {
  --ink: var(--color-text1-4, #1B1B1B);
  --canvas: var(--pod-page-bg-color, #F6F1E8);
  --accent: var(--oyd-editorial-accent, #C1451D);
  color: var(--ink);
  background-color: var(--canvas);
}
.editorial-panel { background-color: var(--pod-card-bg-color, #FFFCF6); }
.editorial-heading { font-family: var(--oyd-editorial-heading-font, Georgia, serif); }
.editorial-content { max-width: var(--magazine-content-max-width); margin-inline: auto; }
.editorial-cover { background-image: var(--magazine-cover-image); }
.editorial-panel { box-shadow: var(--magazine-panel-shadow); }
.editorial-action { transition: background-color var(--magazine-motion-duration) ease; }
@media (prefers-reduced-motion: reduce) { .editorial-action { transition: none; } }
```

fallback 只用于变量暂不可用的兜底，不能作为线上主题已加载的证据。不要在页面根写 `--canvas: #F6F1E8` 等固定基础色盘，也不要重新声明平台 token 覆盖应用主题。局部插画、照片和装饰允许有独立颜色，不强制把所有色值归为品牌色。

antd 控件按 Canvas 技能接入 `CanvasThemeProvider`，由适配层读取当前根容器的计算样式；Provider 不会替换页面中写死的 CSS，也不代表每种字体、圆角和组件参数都已自动适配。实际控件仍需核对消费关系。

发现已确认的全局风格没有对应变量时，先补设计源：Plan 修改 `visualStyle.tokens` 后重新 `materialize`；Fast 更新 `design.md` 后运行带 `--design-file` 的 `sample`。读取生成的 token，上传返回的同一份主题文件，再检查页面。不要只改生成后的 CSS，也不要靠复制色盘到各页补救。

## 验证主题是否真正一致

1. **设计与文件**：逐项对照已确认的导航、框架、主色、页面底、面板、文字、字体及特色强调，确认它们出现在生成的主题 token 中，页面用的是同一角色。导航明暗与模板或自由创意决策一致，导航状态、形状与密度保留本项目设计。文件名叫 `app_theme.css` 或 `app-theme.css` 不影响契约，以本次输出路径为准。
2. **绑定**：`themeVerification.verified=true` 仅证明应用设置绑定了主题资源。`iframePropagation` 是配置字段，不是当前页面主题加载的检测结果；不能凭它为 `false` 就断言 Canvas 收不到变量，更不能据此改成固定色盘。
3. **运行态**：检查实际导航及其默认、悬停和选中状态，并对照应用框架、原生列表、提交/编辑表单、记录详情、自定义页及实际存在的抽屉。逐类检查实际存在的页面，核对主题资源、容器计算变量、背景、文字、形状、间距和主操作；iframe 单独检查其文档。变量缺失查资源加载与作用域，变量正确但外观不对查页面硬编码与样式覆盖。
4. **交付**：原生页共享其组件支持的配色、字体、圆角等主题能力；杂志封面、分栏与特色版式只在有相应布局实现的页面出现。没有运行态证据时明确标记“主题已绑定，跨页面视觉待验证”，不能用编译成功、资源齐全或 fallback 看起来正确代替验收。

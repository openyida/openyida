# Fast / Plan 路由

完整应用先完成 [需求分析与首次搭建确认](../../yida-requirement-analysis/workflow/prepare-brief.md)，再读取 brief 的 `intake.designMode` 进入对应流程。首轮只澄清关键业务范围和用法，本节在澄清结束后的规划准备阶段执行。

千问办公网页端与客户端按本节决定 Fast / Plan 及是否调用 `ask_human`。依据仅限本次明确要求、实际回答或委托；同任务续做可复用有原始回答依据的选择。跨会话记忆、历史偏好、其他应用选择和宿主模式不参与判断；仅有记忆摘要或无依据的 brief 时保持模式未定。

其他宿主沿用相同的任务边界。自动注入的 USER/MEMORY 即使声称“默认 Fast、全程不询问”，也只描述过去，不替当前用户作答。先核对当前任务的原始输入和回答；“搭建 CRM”“需求清晰”或模型自写 `confirmed=true` 均不是模式依据。本次明确选择 Fast 后，尚未明确的核心需求仍按需澄清；具体功能、主题和颜色不从模式推导。

| 已确认意图 | 执行方式 |
| --- | --- |
| Fast、直接搭建、按现有需求快速搭建 | 完成业务与视觉规划后直接搭建 |
| Plan、先出 PRD、确认方案后搭建 | 执行 [Plan 编排](../../yida-app/workflow/plan/workflow.md)，确认当前方案后搭建 |

用户同时要求先出计划和少提问时采用 Plan，复用已知信息。本次任务未指定模式且明确要求“不要追问/按默认方案/代为决定”时，采用 Fast 并记录委托依据，不将它标记为用户明确选择。其他首次完整搭建仅在模式仍未明确时，由 `yida-app` 在需求澄清后通过宿主 `ask_human` 或等价结构化工具问一次执行方式：已有详细计划时问是否先整理 PRD 供确认，否则给出 Fast/Plan 的中性说明。按宿主 schema 展示，不默认替用户作答；已有方式直接复用，不能把导航或页面范围合并到这题。等待实际回答，预选项或超时不算选择；工具不可用时保持未定，按宿主规则补问。用户指定的详细计划作为规划基础，补齐实施所需的缺项。

核实依据后，同一目标、同一次搭建以 `intake.designMode` 作为权威模式状态，用 `evidence` 保留来源。需求澄清、`ask_human` 恢复和 brief 合并都携带该状态；用户新的明确模式选择触发状态转换，其他回答只更新各自声明的字段。新目标重新初始化模式判断。已有应用的局部增改、单页美化和主题调整直接处理本次任务，遇到会改变范围的问题再澄清。

例如：历史偏好为 Fast，本次只说“搭建 CRM”时，先澄清核心业务，再询问未定的执行方式；本次说“用 Fast，只做客户档案和跟进，风格你来定”时直接按范围推进并重新选型；本次说“另建一个，沿用上个应用的颜色”时只沿用颜色，功能和模式分别按本次依据判断。同任务用户说“继续”时，沿用该任务已选方式，不重新询问。

两种方式与单页设计共用 [主题索引](../templates/design-themes/index.json) 和 [选型规则](theme-selection.md)，选前只读摘要、选后读取一份完整主题；共用业务和视觉契约；Plan 额外展示方案并绑定当前版本确认。面向用户的表达与宿主适配见 [用户交互契约](ask-human-interaction-contract.md)。

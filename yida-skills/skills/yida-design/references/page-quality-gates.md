# 页面质量门禁

本文件为完整应用的页面结构、视觉设计和最终交付提供自检门禁。页面设计必须先通过这些门禁，再交给实现阶段。形状、间距、材质和装饰按选中的共享主题检查；下述通用参考值只补主题未定义项，不覆盖主题明确规则。PRD 负责业务结构、应用主题色和风格摘要，`design.md` 负责完整 UI 设计规则；不要把 `design.md` 内容复制进 PRD。

## 1. 区块丰富度建议

- 综合工作台参考 8-10 个有独立业务价值的 `contentBlocks`，按 PRD 核对内容覆盖，不作为准出硬门槛。
- 计数按区块组算：KPI 组、快捷入口组、列表组、图表组各只算 1 个区块。
- 每个区块写清业务问题、信息关系、数据依据、表现形式、操作联动和状态；沿用已有文档字段。
- 重复指标、重复入口、列表行、图表点、装饰块、空白容器不计数；窄场景可以少于参考数量，并说明业务取舍。

工作台按 PRD 核对内容价值、表现适配和真实操作，不能以区块数量或换色代替业务验收。

## 2. 可实现页面门禁

自定义页面按 [响应式布局与验收](responsive-layout.md) 检查宽屏、重排点前后及最窄容器；控件错位、窄屏保留等高空白、操作裁切、页面整体横向溢出或调宽导致业务状态丢失，均需修复后再交付。设计应明确这些行为，运行态验收覆盖实际内容与状态。

每个实际自定义页须按 [输出契约的八项要点](../workflow/output-design.md#页面设计的八项要点) 写出具体设计。页面外壳、焦点、主内容、动作、上下文、状态与移动端关系都应清楚，但不要求对应同名英文字段。

缺少首屏焦点、主要内容安排或空/载/错反馈，不能交付为可实现设计；“继承主题”只能说明共享规则来源，不能替代页面布局与响应式决定。没有真实内容的可选侧栏、摘要或图形应明确不使用，不能为补槽位造业务。

## 阅读无障碍门禁

适用于新建页面和已有应用美化，覆盖导航、门户、自定义页、表单、详情、报表、抽屉及其他浮层；不能仅检查首页或默认状态。

- **文字看得清**：正文、标签、说明、占位提示、表格和图表文字按实际背景核对，沿用项目文字对比度至少 4.5:1 的要求，不将正常信息套用禁用色。图片、渐变、透明面板和状态变化检查最难辨认的位置；优先调整局部前景或承载文字的底面，保留获批主题特征，需要改变视觉方向时先确认。
- **排版读得顺**：标题层级、正文与辅助信息清楚，字体支持中文回退，字号、字重、行高和行宽适合实际内容。空间不足时重排，不靠缩小文字、极细字重或压紧行距塞下内容。长文本可换行；确需截断时提供键盘和触屏均可使用的全文入口，不能只靠鼠标悬停。
- **放大仍完整**：文字放大至 200% 后内容和操作不丢失、不重叠、不裁切；在 320 CSS px 宽度或等效缩放下，普通阅读内容能重排，不要求整页左右来回滚动。确需二维布局的表格、图形可在自身区域滚动，其标题、说明和操作仍需适应容器；不禁止浏览器缩放。
- **含义不只靠颜色**：状态、必填、错误、链接和图表分类配合文字、图标或线型表达。字段保留可见标签，占位文字不能代替标签；错误说明关联对应字段。关键数字、单位和结论使用可读取的文本，图表提供文字摘要或可访问的数据入口，不把必要信息只画进图片。
- **辅助阅读可用**：设计明确标题、列表、表头与字段标签的语义关系；视觉顺序、DOM 阅读顺序和键盘顺序一致。信息图片有等价文字，装饰图不重复朗读，图标操作有可访问名称；展开全文、切换标签和打开详情可用键盘完成，焦点清楚且不被浮层遮挡。

在共享组件规则和逐页验收中写明实际适用项。Fast 随当前页交接，文档任务记录到 `design.md`。实现后检查长内容、错误提示、选中状态、窄屏和放大状态，并用键盘及读屏检查主要阅读路径。发现信息不可读或不可获取时先修复；未执行的检查明确标为待验证。静态配色通过不等于阅读无障碍验收通过，也不能据此宣称符合完整无障碍标准。

缩放与重排依据：[W3C 文字缩放](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html)、[W3C 内容重排](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)。

## 3. 低密大卡片门禁

以下形态不通过：

- 标题下面直接铺 4 个等宽大 KPI 白卡。
- 状态摘要条横跨整页，但只有几个数字和大量空白。
- 快捷入口平铺成孤立图标卡阵列。
- 空数据时放 160px 以上大空白卡片，只写“暂无数据”。
- 右侧或下方大面积留白，没有任务、记录、动态、洞察、提醒或下一步动作。
- 所有区块都使用同一种卡片容器，没有无框区、细线面板、浅底条、列表行、表格或侧栏变化。
- 使用大圆角但配套过大的 margin 或空白高度，导致卡片漂亮但信息密度过低。

修正方式：

- KPI 改成 64-88px 紧凑摘要条、分段摘要或侧栏小面板；如果横向占满宽度，必须补充趋势、更新时间、筛选、主操作或风险状态，不能只有稀疏数字。
- 高频动作改成按钮组、工具条或紧凑入口，低频动作折叠。
- 空态保留当前业务视图的必要上下文，并提供登记、刷新、补录或查看配置动作；不要求改成列表。
- 业务已有风险、提醒、负责人、最近动态、洞察或下一步建议时可以用于右侧；没有这些内容则收窄或移除空栏。

圆角、间距与呼吸感门禁：

- 卡片、控件、浮层与标签按主题的用途映射取圆角，不能统一使用一个大圆角；未定义项可参考业务卡片 20-24px、控件 10-14px。
- 密度与主题和业务任务一致；主题未定义时参考页面边距 20-28px、gap 12-18px、padding 22-28px、列表行 44-56px、主操作 36-40px，不把这些数值当作所有主题的硬门槛。
- 页面布局按主题保留稳定分组间隔，主题未定义时可参考 14-24px；区块内部文本、按钮和状态标签不能贴边；同一组信息内部更紧凑，跨组信息通过间距、浅底条或细线分开。
- 呼吸感不是低密留白：如果某个红框区域只有 1-2 行内容却占据大块高度，必须压缩高度、改成薄行/侧栏/工具条，或补充真实业务信息和下一步动作。
- 空态高度默认 88-120px 内；超过 120px 时必须包含解释、下一步动作、示意图或配置入口，超过 160px 的纯空白卡不通过。
- 截图验收时，如果红框区域内部内容少于 3 个信息点或 1 个动作，必须压缩高度/宽度，或补充最近记录、动态、风险、负责人、说明和下一步动作。

## 4. 主题一致性门禁

- 图标与紧贴的底色一起配色：无底盒时用可读文字色，浅底配深图标，实色底按实际对比度选前景，不能默认白色就清楚。业务图标与相邻底色至少达到 3:1；保留品牌主色，优先调整局部前景或底盒。
- 在页面中核对图标的最终颜色、描边/填充和父级透明度，覆盖默认、悬停、选中与暗色状态。渐变、图片和半透明底色检查最难辨认的位置，必要时加稳定底色；不能靠阴影或加粗描边代替配色修正。CLI 只检查设计中已登记的配色，不能代替实际画面验收。
- 按 [共用主题与验收规则](application-theme-consistency.md) 核对全局风格已写入变量、自定义页引用相同角色，并分别检查已有原生页和自定义页；只有资源绑定证据时标记视觉待验证。

- 导航、按钮、指标和图表按项目颜色角色搭配，不以全部同色为验收标准；对照整页检查主次、颜色面积、前景可读性和跨页一致性，模板默认色不能覆盖项目设计。
- 模型生成的业务色相只作为辅助色、浅背景、图表第二序列或装饰气质；最终以当前项目 `design.md` 和应用主题关系为准。
- 沉浸页、自绘壳、独立品牌页、活动页和公开落地页使用当前应用主题，差异通过布局、材质、素材和构图表达。
- 默认业务页使用 light 模式；暗色只用于用户明确说暗色、夜间、高对比、黑金或暗色科技风。
- 主色不能无思考地固定为 `podBlue` / #1677ff；缺少主题证据时先根据行业、品牌、业务情绪和视觉目标做创意色彩判断，再选择平台预置主题或自定义 token；不得套用“科技=蓝、宠物=橙、法律=蓝”这类行业刻板配色。
- 应用主题设计必须生成 CSS 文件，完整保留平台实际生成的 `--color-brand1-1/2/3/5/6/9/10` 色阶，并以 `--color-brand1-6` 字面量声明主色；不得补造 `--color-brand1-4/7/8`。

## 5. 视觉层次门禁

需要“玻璃感、质感、高级、丰富、惊艳、驾驶舱、工作台打磨、卡片太平、页面太空”时，`design.md` 必须写清视觉层次，不建议只输出无层次的白底白卡。PRD 只引用 `design.md` 中的相关章节。

在正文相应章节说明以下设计含义，避免再建立一份字段副本：

- 画布、表面与层次：背景、内容面、边界、阴影、共容器或留白如何区分内容。
- 色彩角色：品牌、辅助、语义、图形与中性色分别服务什么信息。
- 形状与密度：容器、控件、浮层的圆角、内距、组间距与信息行高如何消费主题 token。
- 呼吸节奏：组内/组间关系、内容安全内距、空内容压缩与移动端重排。
- 需要玻璃或光效时：材质参数、背景关系、文字对比与动效降级。

背景层推荐要求：

- 页面根容器推荐避免无层次的纯空白画布；可使用 `softTintCanvas`，也可使用近白画布 + 淡渐变、细线、星芒、局部装饰、插图或内容密度形成背景感。
- 页面背景与内容层次符合主题定义；色差、细边框、共容器和留白都可承担分组，不能用通用浅底白卡或强投影覆盖已选主题。
- 背景 primitive 仅在主题或用户需要时启用：`topIrregularWash`、`radialGlowWash`、`flowLight` 或 `organicNoise`；平整画布主题无需加装饰。
- `topIrregularWash` 用在首屏顶部、登录页侧图、品牌页或空状态安全区，可以是波浪、斜切、流体色块、有机边界、轻装饰曲线或图形标记；内容排版仍按规则网格对齐。
- `radialGlowWash` 是大面积柔和光洗，不是离散装饰圆球、bokeh 或随机漂浮点；不能遮挡文字和控件。
- `flowLight`、流动线条或光影动效只允许低速、低对比、低透明度，并必须写 `prefers-reduced-motion` 静态降级。
- `organicNoise` 只能作为 0.02-0.06 透明度的微噪点或细纹理，增强质感但不能影响阅读。
- B 端页面遵守“背景可以不规则，内容必须规则”：背景层可以自由，内容区必须保持栅格、分栏、对齐、行高和操作位置稳定。

玻璃感页面的最低要求：

- 页面建议有至少 2 层背景：基础底色 + 弱渐变/径向光/素材遮罩/细线装饰。
- 玻璃面板使用半透明表面、细边框、柔和阴影和 `backdrop-filter`；避免退化成普通纯白不透明卡片。
- 色彩至少包含应用主色、1-2 个辅助色和稳定语义色；辅助色用于图表、状态或分组，不随机涂满卡片。
- 卡片、列表、图表和右侧上下文的容器形态要有差异，不能全部是同一种白卡片。
- 已确定玻璃材质时保持半透明关系；其他主题中的渐变可以搭配主题指定的实色表面。

## 业务图片与场景门禁

所有页面按[任务驱动的视觉设计](task-driven-visual-design.md)检查：图片是否帮助识别实际对象，记录与图片是否匹配，有图/缺图/加载失败时主操作是否完整，图片是否挤占关键数字。固定素材和动态记录图片分别走素材清单与数据绑定，不以装饰图数量判断完成度。没有图片不自动判失败，但有可用图片且能帮助识别、解释或传达氛围却全部忽略时应说明任务依据；用网络或生成图片冒充真实对象照片不通过。

## 6. 双文件输出门禁

每个完整应用设计必须输出两份文件：

- `prd/<项目名>/prd.md`：业务、资源、页面结构、数据来源、主操作、顺序和验收。
- `prd/<项目名>/design.md`：主题 token、视觉特征、布局密度、表面材质、场景配方、组件规则和状态规则。

每个 display 页面在 PRD 中必须输出薄 `pageSpecHandoff`，并至少包含：

```markdown
- pageSpecHandoff：
  - pageStructure：<workbench / dashboard-overview / business-list / detail-profile / split-pane-detail / portal-shell-home / official-homepage / data-screen>
  - scene：<workbench / dashboard / list / detail / landing / screen>
  - contentBlocks：<业务推导的区块与用途；综合工作台参考 8-10 个独立业务区块，子项不分别计数>
  - themeSummary：<应用主题色 / 风格关键词 / 主题交付方式摘要；必须与 design.md 一致>
  - designFile：<prd/<项目名>/design.md>
  - designRefs：<themeProfile / sceneRecipes.<scene> / components.<name> / states.<name>>
  - dataBinding：<form / report / connector / static-empty>
  - primaryAction：<主操作和打开方式>
```

`design.md` 的每个实际自定义页必须有具体八项要点和可定位 anchor。共享视觉、组件与状态规则只写一次；frontmatter 仅保存机器字段与引用索引，不复制正文。

Fast 新建应用按 [阶段输入映射](../../yida-app/references/fast-context.md) 核对已确认需求、主题 CSS、当前页设计与真实回执。已有设计文档和 PRD 的交接使用 `openyida check-design <design.md> --prd <prd.md> --json`，PRD 就绪前可先做单文件校验。Plan 在物化时使用同一校验。文档交接需要有效的 `pageSpecHandoff`、设计引用和逐页设计。

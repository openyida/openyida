# 页面体验模式预设库

## 用途

在 Step 3 已独立生成页面结构需求后读取，用于选择 `preset / adapted / custom` 页面模式。它只定义信息组织与交互骨架，不参与视觉主题确认。

## 目标

本文件用于根据 PRD 和页面规划确定页面的信息组织与交互骨架。页面模式回答“页面如何承载已经确定的业务任务”，不回答颜色、圆角、阴影、品牌表达等纯视觉问题。

页面模式的机器可读标准字段由 [页面模式索引](../templates/page-patterns/index.json) 维护。2.0 源 JSON 只写 `id`、选择原因和项目 `adaptations`；`mode`、`mustKeep`、固定丰富度要求与全局防填充规则由 materialize 从索引补齐。

页面模式不进入视觉 `ask_human`。它由核心任务、页面结构需求、内容优先级、信息密度和交互重心自动确定，并写入 `pages.customPageDetails[].layoutPattern`。预设是参考基线，不是必须套用的答案。

## 先生成页面结构需求

匹配预设前，必须先根据 PRD 独立完成当前页面的结构需求，不得先选预设再倒推页面内容。结构需求至少包括：

1. 核心用户与核心任务。
2. 任务流和对象关系。
3. 内容优先级与首屏结构。
4. 主要操作、状态反馈和异常处理。
5. 上下文、关联记录和辅助决策信息。
6. 信息密度与移动端要求。
7. 内容丰富度要求。

### 内容丰富度

每个自定义页面默认要求 `rich-but-relevant`：内容要丰富，但所有内容必须服务核心任务，不得用无意义 KPI、重复快捷入口、装饰卡片、空洞图表或大段占位文案凑数量。

页面结构应按实际任务覆盖以下内容层，适用项不得缺失：

- 决策层：用户进入页面首先需要判断的状态、重点或主张。
- 主任务层：完成核心任务所需的对象、数据、内容和操作。
- 上下文层：关联对象、历史记录、进度、来源或说明。
- 异常层：风险、逾期、冲突、空态、错误和无权限。
- 承接层：下一步动作、处理结果、跳转去向或转化入口。

“内容丰富”按页面任务衡量，不按区块数量衡量。单一提交页可以比工作台区块更少，但仍要覆盖任务说明、分组填写、辅助提示、校验、提交反馈和后续动作。

## 轻量匹配顺序

完成页面结构需求后，再读取下面的预设并执行一次轻量匹配：

1. 用核心任务和关键交互寻找最多两个可能的预设，不给全部预设逐项评分。
2. 核心任务和交互骨架都强匹配时，使用 `mode=preset`。
3. 核心任务匹配，但页面结构存在项目特有要求时，使用 `mode=adapted` 并列出 `adaptations`。
4. 没有明显强匹配，或预设会删除重要内容层时，使用 `mode=custom` 和 `id=custom-page-pattern`。
5. 最后用信息密度、响应式和内容丰富度校正结果。

不得因为用户选择了某个视觉主题、品牌色，或页面中存在 KPI、表格、图表、右侧栏，就改变页面模式。

## 页面模式清单

### enterprise-control

适合：多对象、多流程、多页面的企业内部管理页面。

强触发：查询、管理、协作、审核；中高信息密度；需要稳定导航、筛选、表格和详情区。

设计骨架：顶部轻量上下文 + 主工作区 + 右侧或底部辅助信息；主要操作固定在工具栏或区块右上角，次级操作收敛。

必须保留：清晰业务边界、高效扫描、稳定的状态与操作位置。

避免：大面积空白卡；只有指标没有任务承接。

### compact-workbench

适合：首页、工作台、团队入口、日常处理中心。

强触发：用户每天打开；需要判断优先级；存在待办、最近记录、提醒和高频入口；首屏需要承载多类信息。

设计骨架：紧凑状态摘要 + 主任务列表 + 最近记录 + 上下文提醒；快捷入口使用小按钮组或紧凑入口行；空态使用薄提示行。

必须保留：高频动作显眼、分组清楚、首屏至少两层信息。

避免：四个等宽大 KPI 卡后直接进入大空态；重复快捷入口凑内容。

### data-insight

适合：经营看板、销售分析、运营指标和趋势判断页面。

强触发：核心任务是看趋势、找异常、比较指标；图表是判断依据而不是装饰。

设计骨架：关键指标 + 主趋势区 + 异常洞察 + 明细承接；指标显示口径、周期和变化方向；图表与明细互相解释。

必须保留：数据层级、异常与趋势、指标口径。

避免：只有图表没有业务解释；颜色过多影响判断。

### action-command

适合：任务分派、审批处理、工单处置、客服跟进和销售行动台。

强触发：用户需要判断“现在先处理什么”；页面有优先队列、推荐动作、批量处理和状态闭环。

设计骨架：行动摘要 + 优先队列 + 当前处理对象 + 结果反馈；主操作靠近任务内容。

必须保留：行动优先、当前任务突出、反馈明确可追踪。

避免：把任务队列做成普通数据列表；主操作远离当前对象。

### progress-narrative

适合：项目进度、服务交付、维修巡检、活动筹备和阶段推进。

强触发：核心信息是阶段、里程碑、责任人、下一步和风险。

设计骨架：阶段总览 + 时间线 / 里程碑 + 当前风险 + 责任人；详情承接记录与附件。

必须保留：阶段感、责任归属、下一步动作和风险。

避免：把阶段压缩为普通表格；只写状态不写下一步。

### catalog-browse

适合：商品、课程、资产、模板、案例、门店和知识条目浏览。

强触发：核心任务是搜索、筛选、比较和选择对象；对象适合卡片、缩略图、标签和摘要。

设计骨架：筛选区 + 结果控制区 + 稳定高度的对象卡片或列表；明确排序、筛选和结果反馈。

必须保留：筛选路径、对象可比较性、稳定卡片高度。

避免：内容高度跳动；没有排序或结果反馈。

### form-focused

适合：单页表单、报名、申请、配置、信息采集和轻量提交页。

强触发：核心任务是填写或提交；移动端或低干扰体验重要。

设计骨架：任务说明 + 分组表单 + 辅助提示 + 提交结果；错误反馈靠近字段；复杂说明折叠。

必须保留：填写路径、即时校验、明确提交结果。

避免：加入无关图表或大背景；隐藏关键说明。

### brand-landing

适合：官网、品牌展示、活动页、产品介绍和线索转化页。

强触发：面向外部访客；需要首屏主张、信任背书、真实素材和行动入口。

设计骨架：首屏主张 + 产品 / 服务说明 + 场景或案例 + 信任背书 + 行动入口。

必须保留：明确主张、真实素材、清楚 CTA。

避免：只有抽象口号；编造图片 URL 或案例数据。

说明：`brand-landing` 是页面模式，不代表必须采用“鲜明品牌”的视觉主题。它可以与克制清晰、柔和现代或鲜明品牌等主题组合。

### split-pane-ops

适合：左列表右详情、处理台、客服工作区、对象审核和批量分拣。

强触发：用户频繁在列表和详情间切换，需要保留上下文；详情包含操作、历史、附件或评论。

设计骨架：筛选与列表 + 详情面板 + 操作区；当前选中项、加载和空态清楚；移动端改为列表到详情的单列切换。

必须保留：稳定主从关系、上下文不丢失、当前对象和反馈清楚。

避免：详情区过空；列表和详情层级混乱。

## 选择输出

下面是 materialize 补齐后的完整逻辑结构示例；模型写入 2.0 源 JSON 时遵守[紧凑写入契约](build-plan-compact-schema.md)，不要复制标准字段：

```json
{
  "layoutPattern": {
    "mode": "adapted",
    "id": "compact-workbench",
    "reason": "该页面是采购团队每日入口，需要在首屏判断待办、临期和异常优先级。",
    "adaptations": [
      "增加持续展开的采购上下文区，承接供应商、订单和最近沟通记录"
    ],
    "mustKeep": ["高频动作显眼", "首屏至少两层信息", "空态使用薄提示行"]
  },
  "contentRichness": {
    "requirement": "rich-but-relevant",
    "contentLayers": [
      "决策层：临期、异常和待处理事项",
      "主任务层：按优先级排列的采购任务",
      "上下文层：供应商、订单和最近沟通记录",
      "异常层：报价不足、收货差异和三单匹配异常",
      "承接层：新建申请、询价、下单和收货入口"
    ],
    "antiFiller": ["不使用无业务承接的等宽 KPI 卡", "不重复快捷入口凑区块数量"]
  },
  "density": "compact"
}
```

## 冲突规则

- 页面核心任务和视觉主题冲突时，页面核心任务决定页面模式；视觉主题只调整视觉表达。
- 同一应用允许不同页面使用不同页面模式，但必须共享同一个全局视觉主题和组件体系。
- 一个页面存在多个任务时，以首屏最高优先级任务选择主模式，其余任务作为区块级变体。
- 只有存在核心任务与交互骨架的强匹配证据时，才能直接使用 `mode=preset`。
- 部分匹配必须使用 `mode=adapted` 并写明结构改造，不得把项目特有需求塞进预设名称中省略。
- 没有强匹配时直接使用 `mode=custom` 和 `custom-page-pattern`，不需要证明所有预设都完全不适合。
- 如果核心任务明显不同的多个页面全部使用同一个预设，必须重新检查一次；不得为了追求模式多样性而强行选不同预设。
- 预设、改造和自定义模式都必须满足 `contentRichness.requirement=rich-but-relevant`。

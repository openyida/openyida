# 搭建计划内容规则

## 用途

在生成 `build-plan.json` 的五类计划内容，以及从同一事实源派生 `prd.md` 时读取。它定义“计划里必须写什么”，不负责 JSON 字段形状、视觉主题候选或 HTML 维护。

搭建计划严格对应需求文档 3.3-3.7。章节顺序固定：

1. 需求总览
2. 数据模型
3. 业务流程
4. 页面规划
5. 视觉风格

## prd.md 与 build-plan.html 的关系

`prd.md` 和 `build-plan.html` 使用同一个 `build-plan.json` 事实源，但面向不同读者采用不同展示结构。

- `prd.md` 是搭建计划的 Markdown 版，给后续 AI 开发读取。
- `build-plan.html` 是搭建计划的标准 UI 版，给用户确认。
- `prd.md` 保留 5 个章节：需求总览、数据模型、业务流程、页面规划、视觉风格。
- `build-plan.html` 使用 4 个主章节：需求总览、数据模型、业务流程、页面规划；视觉概览和主题色合并到需求总览，不设置独立视觉章节。
- 两者的业务结论必须一致，不能各自推导不同的数据模型、流程或页面。
- `prd.md` 可以使用 Markdown 表格、列表和小标题；不写 HTML UI 结构，不写 `ask_human` 过程，不展开完整 `design.md`。
- 视觉风格在 `prd.md` 中只写用户可理解摘要，并引用已同步生成的 `design.md` 作为完整设计契约来源。
- `prd.md` 顶部记录 `buildPlanRevision`，必须等于 `build-plan.json.meta.revision`；用户确认后作为后续开发的产品执行基线。

## 1. 需求总览

目标：让用户确认 AI 对核心需求的理解是否正确。

必须包含：

- 应用概述：一段结构化文字，融合应用名称、应用定位、核心用户群体、核心业务对象和 1-3 个核心问题。
- 业务全景图：必须是“全部表 + 表间关系”的对象关系图。图中每个节点代表一张表 / 表单，每条连线标注关系类型，例如“包含、关联、产生、承接、依赖、回款跟踪”。不要只画流程节点，也不要只输出 Mermaid 文本。
- 数据模型摘要：每个核心对象一句话。
- 流程关系摘要：每条流程一句话，格式为“流程名称：一句话说明”。
- 导航菜单摘要：按用户进入应用后的菜单组织方式列出主要入口，每个入口一句话说明；可承接页面规划摘要，但在需求总览中展示为“导航菜单”。
- 角色与权限摘要：每个角色一句话权限范围。
- 视觉设计摘要：一句话风格 + 主题色。

应用概述不要写成表格填空；要写成用户可读的一段话。

需求总览布局规则：

- 需求总览使用文档式小节流，不使用卡片宫格。
- 小节顺序固定为：应用概述、业务全景图、数据模型、业务流程、权限、导航菜单、视觉设计。
- 每个小节包含标题、灰色说明和正文；正文优先用短段落或项目符号。
- “权限”在需求总览中只写一句话范围摘要，不追问角色权限细节。
- 业务全景图放在“业务全景图”小节内，图前可写一段对对象关系的简短说明。

业务全景图生成规则：

- 节点必须覆盖 `dataModels` 中的全部表单 / 数据表，不得遗漏孤立但需要创建的表。
- 边优先来自用户输入、附件表头关系、模板抽取结果和字段中的关联表单关系。
- 用户未明确说明时，AI 可以基于业务常识推断表间关系，但关系标签要写成用户能理解的业务词。
- 关系图表达的是数据对象之间的结构关系，不是审批节点、页面跳转或技术执行链路。
- 若一个表既参与数据关联又参与流程承接，例如“报价”承接“商机”并产生“合同”，需要在图中明确展示。

## 2. 数据模型

目标：确认业务对象、表单和字段设计。

每个业务对象 / 表单必须包含：

- 表名称
- 表单类型
- 一句话描述
- 视图：全部数据、我提交的、表单提交等
- 字段表格

字段表格列固定：

```text
字段 | 字段类型 | 必填 | 默认值/选项 | 关联关系 | 分组 | 说明
```

字段粒度要求：

- 字段名使用业务语言，不使用技术 ID。
- 字段类型写宜搭可理解的类型，例如单行文本、数字、单选、日期、成员、附件、关联表单。
- 必填写“是 / 否”。
- 默认值/选项没有时写 `-`。
- 关联关系没有时写 `-`。
- 分组用于后续 Divider 分割线语义分组。

## 3. 业务流程

目标：定义业务对象之间的流转逻辑，包含审批流和自动化规则。

每条流程使用一张流程卡片，包含：

- 流程类型：自动化 / 审批流 / 业务流
- 流程名称
- 触发时机
- 节点链路，例如“提交报价 → 销售主管 → 审批通过”
- 业务说明
- 规则说明：自动化规则、审批规则、分支条件、驳回重提逻辑

示例：

```text
[审批流] 报价审批                       触发：提交报价时
提交报价 → 销售主管 → 审批通过

销售代表在商机中发起报价，填写产品明细、金额与折扣。
分支条件：折后金额 ≤ 10 万 → 销售主管单人审批；折后金额 > 10 万 → 销售主管 → 财务审批人两级审批。
```

不要写技术执行流；只写业务流。

## 4. 页面规划

目标：确认应用会有哪些页面，以及自定义页面的结构和体验。

页面规划分两块：

### 页面总览

表格列固定：

```text
页面名称 | 类型 | 用途
```

页面类型可用：

- AI 自定义页面
- 宜搭表单
- 宜搭流程表单
- 报表 / 看板

### 自定义页面详情

每个自定义页面一张卡片，包含：

- 名称
- 页面定位
- 核心用户与核心任务
- 内容优先级
- 功能区块
- 首屏结构
- 标志性交互
- 内容丰富度：覆盖适用的决策、主任务、上下文、异常和承接层，并列出避免的填充内容
- 页面模式与信息密度
- 视觉应用
- 权限说明

页面详情要让用户能想象最终页面能做什么、内容如何组织以及全局视觉主题如何在该页面落地，不要只写“展示数据、快捷操作”这类泛化描述。内容默认要求丰富但与任务相关；丰富度按任务覆盖衡量，不按区块数量衡量。

字段归属：

- 页面定位、核心用户、核心任务、内容优先级、功能区块、首屏结构、标志性交互、内容丰富度、页面模式、信息密度和权限属于 `pages.customPageDetails[]`。
- “视觉应用”在 `prd.md` 的自定义页面详情中显示，数据来自 `visualStyle.forUser.pageApplications`；`build-plan.html` 不重复展示逐页视觉应用。显示差异不改变决策归属或事实数据。
- 页面模式读取 [page-patterns.md](page-patterns.md)：先独立生成页面结构需求，再用 `preset / adapted / custom` 轻量匹配，不进入视觉 `ask_human`。
- 页面规划决定“突出什么”，视觉设计只能决定“用什么视觉语言突出”，不得修改已确定的内容优先级。
- 不允许用无业务承接的 KPI、重复快捷入口、装饰卡片、空洞图表或占位文案制造虚假的内容丰富。

## 5. 视觉风格

目标：展示 Step 2 已选择或推断的项目视觉方向，以及该方向在页面规划上的具体应用，并与已同步生成的 `design.md` 保持一致。主题模板身份只用于内部物化，完整设计系统由 `design.md` 承载。

`prd.md` 的“视觉风格”章节必须包含用户可理解的内容：

- 一句话视觉方向 + 色彩策略
- 导航结构（顶导/侧导）与导航明暗（浅色/深色）
- 用户视觉偏好：来自用户输入、视觉方向选择或 AI 推断，不包含模板名称、页面任务或内容优先级
- 风格来源：用户指定 / 图片参考 / AI 推荐 / 模板继承
- 视觉选择依据：用自然语言说明场景、品牌或用户选择如何影响方向、主题色和导航
- 主题画像摘要：表面语言、对比强度、品牌表达、圆角、阴影、图标和动效
- 页面视觉应用：全局主题如何作用于各主要页面的背景、表面、主操作和状态；每页优先应用 1–3 个满足内容契约的视觉记忆点，不重复布局节奏、信息密度和首屏重点
- 视觉记忆点：汇总选中模板中用户能感知的稳定视觉特征；页面没有匹配内容时保留设计配方，不虚构指标、分类、进度或图表
- 层次与组件摘要：背景与卡片层次、按钮/表格/卡片/标签/抽屉/空态/加载/错误/无权限等状态规则的简要说明
- 图标体系摘要：说明使用一致的线性图标体系，不展示具体组件实现细节
- 素材策略摘要：官网、品牌页、展示页必须写真实素材来源或缺口，不得编造图片 URL
- 应用生成准备：说明已同步生成完整 `design.md`，确认生成应用后会作为后续 AI 开发事实源；搭建计划中不展示完整设计系统

`build-plan.html` 不展开上述视觉风格章节，只在需求总览中展示：

- `overview.visualSummary` 的视觉概览。
- `visualStyle.forUser.colorStrategy` 的主题色名称、HEX 色值和色块。

这只是 HTML 展示收敛，不得缩减最终 `prd.md` 或 `design.md`。2.0 源 JSON 可以按[紧凑写入契约](build-plan-compact-schema.md)省略索引字段和标准规则副本，由 materialize 在生成产物前补齐完整逻辑结构。

`visualStyle` 按展示对象分层：

- `forUser`：源 JSON 保存项目视觉方向、色彩、导航、视觉记忆点绑定和素材差异；materialize 补齐 PRD 所需的主题画像、页面基础视觉应用和用户摘要。
- `internal`：只保存 `selectedTheme` 等物化身份，不进入 `prd.md`、`design.md` 或 `build-plan.html`。
- `forDesignMd`：源 JSON 保存产品形态应用差异；materialize 从主题索引和页面事实补齐内部模板路径、页面模式引用和色彩策略，不在用户可见产物中展开模板身份。

搭建计划中只做用户可确认的摘要，不写完整实现 CSS，也不复制完整 `design.md`。同步生成的 `design.md` 要写当前项目的设计契约。

视觉风格硬规则：

- 不固定默认蓝色，不按行业刻板配色。
- 主题色只服务当前项目设计，不在本技能中判断是否传给 OpenYida 创建或更新命令。
- 页面模式由业务目标、用户任务、页面类型、内容优先级、信息密度和交互重心决定，读取 [page-patterns.md](page-patterns.md)。
- 三套完整视觉方向由用户偏好、品牌资产、参考素材、应用场景和主题索引共同决定；业务领域不机械绑定配色，场景任务可用于解释推荐依据。
- 纯视觉主题只决定整体气质、表面层次、对比度、品牌表达、圆角、阴影、图标、动效和色彩策略；不得改变页面规划。
- 主题色来自用户输入、品牌和素材线索或已确认主题的色彩策略；颜色冲突和素材置信度问题由 `ask_human` 阶段处理。
- 方向名称、体验描述和推荐理由由 AI 根据项目生成；主题身份与模板路径只从 [主题索引](../templates/design-themes/index.json) 取得，不向用户展示。
- `design.md` 按 [visual-design.md](visual-design.md) 读取内部选中主题指向的一份完整模板，集中注入项目视觉方向、主题色和导航事实；不得改写全部主题模板。
- 默认业务工具页使用清晰边界、合理密度和稳定呼吸节奏；避免大留白和低信息密度。
- 页面背景和卡片背景必须有明确层次，不能只靠弱阴影区分。
- 工作台 / 业务首页不能退回“4 个等宽大 KPI 白卡 + 图标快捷卡 + 大空态白卡”的低密模板。
- 不使用 emoji、CSS 图形、字母占位、Unicode 符号或临时 SVG 替代图标。

## 产品形态差异

- `internal_management`：`prd.md` 完整保留 5 个章节；CRM、ERP、采购等业务领域共享同一候选逻辑。
- `frontend_backend_composite`：需求总览和页面规划区分前台 / 后台；共享品牌体系，前台可增强品牌表达，后台采用克制变体。
- `brand_marketing`：数据模型和业务流程可弱化，但页面规划、品牌素材和视觉主题必须更具体。
- `transactional_frontend`：强调商品 / 服务素材、价格与转化链路，但这些内容优先级仍由 PRD 决定。
- `single_task_form`：页面规划和数据模型优先，业务流程可只写提交 / 审核 / 通知链路。
- `data_monitoring`：指标口径、异常和实时状态优先；是否使用深色主题仍由用户偏好和展示环境决定。
- `content_browse`：内容结构、筛选与真实素材优先，视觉主题侧重排版和表面语言。

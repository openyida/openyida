# Step 2：确认应用范围与视觉方向

## 目的

让 AI 根据用户诉求自主判断是否需要确认应用范围，并基于应用场景生成三套可落地的完整视觉方向。计划生成前原则上只执行一次结构化 `ask_human`，最多包含两个逻辑问题。

## 输入

- Step 1 输出的需求上下文。
- [build-plan-content.md](../references/build-plan-content.md) 定义的必需内容。
- [视觉方向选择规则](../references/visual-theme-selection.md)。
- [用户交互与可见表达契约](../../../references/ask-human-interaction-contract.md)。

## 操作

### 1. 先判断是否需要确认应用范围

`ask_human` 不是固定问卷。AI 先读取用户输入和需求来源，再判断现有信息能否形成清晰一致的应用范围。

以下任一信息已足以确定主要范围时，不询问应用范围：

- 用户明确列出功能模块；
- 用户说明核心业务场景、主要用户任务或关键业务流程；
- 可读需求文档、功能清单、数据表或参考应用已给出清晰范围；
- 用户明确要求采用默认方案、推荐方案、直接规划或不再提问。

只有输入停留在宽泛应用名称或目标，例如“生成一个 CRM”“做一个采购管理应用”，且缺少模块、任务、流程等范围证据时，才生成一个与当前场景相关的多选问题：

- 问题只确认“这个应用主要包含哪些业务模块”；
- 提供 3–6 个高频且互不重复的场景选项，第一组合理默认标记为推荐；
- 允许用户补充自定义模块；
- 回答写入 `overview.moduleScope`，并同步用于推导对象、流程和页面范围；
- 不继续逐项追问字段、视图、首页、看板、角色权限、审批、自动化或流程细节。

审批是否存在由 AI 根据所选模块、业务对象和常见流程推断，并在搭建计划中作为可调整方案呈现。只有用户输入与可读来源对同一关键事实存在无法兼容的冲突，且采用任一分支会改变整个应用边界时，才可用范围问题一并化解；不得单独固定询问“是否需要审批”。

### 2. 生成三套完整视觉方向

业务范围达到可规划状态后，AI 从已知事实中提取以下场景特征：

- 以关系经营还是流程执行为主；
- 以协作、执行、分析还是服务为主；
- 主要使用频率和信息密度；
- 期望的产品气质；
- 品牌色、Logo、参考界面和明确视觉约束。

然后只读取 [主题索引](../templates/design-themes/index.json)，生成恰好三套完整视觉方向。每套候选必须同时确定：

- `directionId`：当前交互内唯一标识；
- `directionLabel`：AI 根据项目场景生成的用户可见名称；
- `description`：用户可感知的整体体验说明；
- `themeId`：绑定到主题索引中的有效记录，仅供内部执行；
- `primaryColor` 与 `primaryColorName`；
- `navigationStructure`：`top` 或 `side`；
- `navigationTone`：`light` 或 `dark`；
- `recommendationReason`：为什么适合当前场景。

候选生成必须满足：

1. 第一项为 AI 推荐项，并基于当前应用场景解释原因。
2. 三项绑定三个不同的有效 `themeId`。
3. 任意两项至少在主题基底、主题色、导航结构、导航明暗四项中的两项不同。
4. 不得仅凭“企业内部、专业、稳重”默认选择蓝色、浅色侧边导航。
5. 用户已有品牌或视觉要求优先；如果只明确了品牌色，三项均保留该颜色，通过主题基底、导航结构和导航明暗形成差异。
6. 先定义适合项目的视觉方向，再绑定核心视觉 DNA 相符的主题索引记录；索引中没有可落地模板的方向必须在展示前丢弃并重新生成。
7. 色彩和导航允许作为项目级覆盖；表面层级、形状语言和核心交互机制与模板明显冲突时，不能强行绑定。

候选阶段不得读取任何完整主题 Markdown，不得生成三份 `design.md`，也不得临时拼接主题模板。

### 3. 一次执行计划前确认

计划生成前原则上只执行一次结构化 `ask_human`：

- 范围不足：同一次交互包含“应用范围”和“视觉方向”两个逻辑问题；视觉候选基于应用场景和 AI 推荐范围生成。回答后按最终范围校验内部主题绑定，必要时在不改变用户所选方向的前提下重新匹配可落地基底，不发起第二轮常规提问。
- 范围已清晰：只包含“视觉方向”一个逻辑问题。
- 用户已经明确完整视觉方向（主题色、导航结构和导航明暗均明确，或要求严格继承可信品牌/模板）：直接写入，不再询问视觉方向。
- 用户明确要求不再提问或采用推荐方案：AI 选择第一套推荐方向并记录 `source=ai_inferred`，不执行本步骤交互。

用户可见选项只展示 `directionLabel`、`description` 和推荐原因，不展示主题模板名称、`themeId`、模板路径或内部匹配过程。

选择完成后原子写入：

- `visualStyle.forUser.visualDirection`
- `visualStyle.internal.selectedTheme`
- `visualStyle.forUser.colorStrategy`
- `visualStyle.forUser.navigationStyle`

未选中的候选只保留在当前 `ask_human` 的问题与回答历史中，不写入最终 `build-plan.json`。

若用户自定义的视觉方向没有可用模板，执行一次二选一确认：采用最接近的可用基底，或返回三套候选重新选择；不得在运行时拼接新模板。

来源不可读时仍遵循特殊阻断规则：只生成一个来源补齐问题并停止，不生成范围或视觉问题。

若宿主没有结构化提问工具或调用失败，使用相同问题的简短编号文本并停止执行，直到用户回答；不能把普通对话回退当成无需等待的通知。

## 输出

- 可形成可信计划的应用范围事实。
- 用户明确提供或 AI 推断的业务事实和假设。
- `visualDirection`、`selectedTheme`、`colorStrategy`、`navigationStyle` 四组一致的已选视觉事实。
- 可供 Step 3 生成搭建计划的确认上下文。

## 检查清单

- [ ] 计划生成前最多执行了一次结构化交互，且最多两个逻辑问题。
- [ ] 应用范围清晰时没有重复询问模块。
- [ ] 没有固定询问审批、权限、首页、看板、字段、视图或视觉实现细节。
- [ ] 视觉方向恰好三套、第一项推荐，且候选之间有足够差异。
- [ ] 用户可见选项未暴露主题模板名称、ID 或路径。
- [ ] 候选只读取主题索引，未读取任何完整模板。
- [ ] 最终 JSON 只保存选中方向，没有保存未选候选。
- [ ] 来源不可读时只处理了来源，没有进入其他问题。

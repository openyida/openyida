# 判断是否分前后台

收到有效功能选择后，需要新增或修正入口判断时读取。这里的前台和后台都是用户使用系统的页面（访问态）；开发者修改字段、流程和应用配置的 `/admin` 另行交付。

## 判断依据

- **只有访问后台**：本次只给工作人员提供录入、受理、处理或维护业务的页面。办事人通过电话、外部平台或已有入口发起业务，或者本次不需要办事入口。
- **只有访问前台**：本次只提供办理、查询或展示页面。纯展示、查询可能无需人工处理；提交后需要处理的业务，要明确由已有系统、已有人员入口或自动流程承接。
- **不分前后台**：大家使用同一套业务页面，按职责看到不同菜单、数据和操作。适合围绕同一批项目、客户或记录开展工作的情况。
- **分前后台**：办事的人和处理业务的人分别进入适合自己的页面。前台用户能直接办理、查看结果；后台人员处理收到的业务。两边的主要任务、查看内容或操作步骤有明显差异时，建议分开。

不同角色可以使用同一套页面，分别配置权限；同一个人也可以同时使用前台和后台。根据实际任务判断是否分开，系统名称和角色数量只作为背景信息。

“只有访问后台”和“不分前后台”都可以用一套页面加权限实现。前者强调工作人员受理、运营或处理业务，后者强调大家围绕项目、任务等共同工作。需求没有明显的受理或运营关系时，使用“不分前后台”的说法。前后台的划分也不代表公开访问、匿名访问或应用管理权限。

| 已确认的实际用法 | 建议 | 谁使用、看到什么、能做什么 |
| --- | --- | --- |
| 项目成员处理任务，负责人分配任务、查看进度 | 不分前后台 | 使用项目和任务页面，按职责显示数据与操作 |
| 销售维护自己的客户，主管查看团队客户 | 不分前后台 | 使用客户列表和详情，按权限区分数据范围 |
| 客户自己预约，员工安排和处理预约 | 分前后台 | 客户看可预约服务和自己的预约；员工看待处理预约和排期 |
| 员工报修、查进度，维修人员接单、处理 | 分前后台 | 员工看“我要报修、我的报修”；维修人员看“待处理工单、我的工单” |
| 只有维修人员登记、处理和统计外部渠道收到的工单 | 只有访问后台 | 直接使用工单列表、处理页面和所需统计 |
| 员工登记电话预约，或处理外部商城同步的订单 | 只有访问后台 | 员工登记、排期，或审核订单、发货 |
| 本次提供活动报名，工作人员在已有入口处理 | 只有访问前台 | 报名人填写、提交信息，处理沿用已有入口 |
| 本次只展示产品或查询已有进度 | 只有访问前台 | 用户浏览或查询，数据来源按实际需求接入 |
| 团队成员预订会议室，负责人维护可用资源 | 不分前后台 | 共用会议室和预订页面，按职责显示操作 |

## 判断顺序

1. 列出本次实际使用者和任务，明确哪些办理或处理功能已在其他渠道完成。
2. 本次只提供业务受理、运营或维护页面，办理发生在别处或不在本次范围内时，选择“只有访问后台”。仅凭“内部员工使用”不足以判断为后台。
3. 本次只有办理、查询或展示任务时，选择“只有访问前台”。需要处理的提交，须在已有 `entryRecommendation.reason` 和业务流程中说明由谁承接；尚未明确时记入 `openQuestions`，补问实际处理方式，不擅自扩建后台，也不声称业务已完整。
4. 办理和处理都在本次范围内时，比较双方所需页面：任务和内容明显不同，选择“分前后台”；共用业务页面即可完成工作，选择“不分前后台”。
5. 没有明确的办事与受理关系，大家共同维护项目、客户或任务时，选择“不分前后台”，按职责配置菜单、数据和操作。

用户明确只交付某一端时沿用范围，说明它与已有业务的关系。四种说法描述本次交付范围，不要求每个应用都搭建两端。

## 向用户怎么说

直接说明是否分前后台，再列出谁使用、看到什么、能做什么。例如：

- “这个项目管理系统不分前后台，成员处理任务，负责人分配任务、查看团队进度，菜单和数据按权限显示。”
- “这个预约系统分为客户预约前台和员工处理后台，两边共享预约数据。”
- “这个系统只有员工使用的业务后台，员工登记电话预约并安排时间。”
- “本次只做活动报名前台，报名人填写并提交信息，工作人员在已有报名管理页面处理。”

用法不明确且会影响页面规划时，补问具体用法，例如“这个预约系统是让客户自己预约、员工处理，还是只供员工内部登记预约？”已有答案直接复用，用户委托决定时说明建议依据。

## 首页按任务选择

业务后台或不分前后台的系统，先满足实际使用者的高频任务，不因“管理系统”“后台”“暗黑风格”推导出驾驶舱。Fast 与 Plan 使用同一判断：

前台也要确定默认页面和菜单顺序：展示、发现、办理或进度查询，按实际首要任务选择。前后台分别记录“进入后先到哪一页、先看到什么、接下来去哪里”，具体交接见 [每个入口都确定首页与菜单顺序](../../yida-app/references/entry-navigation.md#每个入口都确定首页与菜单顺序)。

| 主要任务 | 入口建议 | 首屏重点 |
| --- | --- | --- |
| 处理多个相关业务任务 | 业务工作台，可采用门户式组织；自定义页 scene 为 `workbench` | 待办、操作队列、业务列表与常用入口，按角色和处理优先级排列 |
| 主要维护一类记录或办理单项任务 | 直接打开原生管理列表、表单或流程入口 | 找到记录并完成当前操作，无需额外创建首页 |
| 已确认的经营分析、指标判断、趋势比较 | 分析页，scene 为 `dashboard`；明确需要投屏监控时为 `screen` | 指标口径、趋势与分析结论；只有分析确为该角色的首要任务时才设为默认首页 |

工作台的“门户式”指将办事入口与当前工作集中组织，不要求再建一套导航，也不固定模块数量。只选择需求中有依据的内容：待处理事项说明对象、状态、优先级及办理入口；操作队列支持需求所需的筛选与处理；常用入口连接真实业务页面。公告、日程、最近访问等仅在有用途时加入。没有汇总价值就直接进入业务列表。

待办数量、逾期数量可作为任务入口的辅助摘要，能跳到对应处理列表；出现这些数字或一张辅助图表，不把整页改为驾驶舱。按业务命名，例如“采购工作台”“待处理订单”，不把所有首页命名为“XX 驾驶舱”。待办来源、处理权限和完成后的状态更新都要有真实依据，不编造任务或接入能力。

在现有 `userTasks`、`entryRecommendation.reason`、页面 `purpose` 中写清“谁进入后先做什么、为什么选择该入口”。分析需求须能追溯到有效功能或用户任务；只有系统名称、管理者身份或视觉偏好时，不自动新增经营分析。方案说明首要任务和办理路径，不让用户回答技术场景枚举。

验收时按角色从首页走完一条真实任务路径，并确认处理后的队列或状态更新。`/workbench` 只是平台入口路径，不证明已经实现业务工作台；改标题也不能代替操作能力。

## 与导航和资源分开

分前后台时，默认在同一个应用内提供两套入口，共用业务数据。是否分前后台与是否创建两个应用分别判断；访问范围与权限按用户要求单独配置。

入口建议确定后，下游 AI 按 [导航决策](../../yida-design/references/navigation-decision.md) 选择各入口的页面承载和菜单。

业务后台处理订单、工单等已选业务；`/admin` 用于应用开发管理。

## 交接要求

在 brief 中用 `userTasks` 关联使用者与有效功能，用 `entryRecommendation` 记录入口建议和依据。用法证据不足时保留待定并补问关键用法；用户委托时记录依据并标记 AI 推导。完成后直接交给下游规划。

# 首轮需求分析

流程：理解需求 → 核心功能候选 → 用户选择或补充 → 判断是否分前后台 → 整合输出。已有充分信息时跳过相应提问。

## 适用阶段与续做

先核对当前需求范围、历史回答和同任务 brief，再决定是否进入下方首轮流程。已有应用或表单不能单独作为需求已确认的依据。

- **首次澄清**：当前范围尚未确认时，按下方流程补齐关键需求；用户已明确的内容直接采用。
- **继续任务**：有效历史回答或同任务 `intake.confirmed=true` 已覆盖当前范围且未被撤回时，复用答案，返回 `yida-app` 的未完成阶段。刷新、恢复、压缩或“继续”不触发重新首问。
- **材料缺失**：brief 丢失但历史答案完整时，用已有答案恢复材料。无法核实的内容保持未确认；只有缺失或冲突会影响下一步时才补问，不重新生成已回答的功能候选。
- **需求变化**：直接更新用户明确新增或撤回的内容，未变化的部分沿用原确认；只补问影响下一步的未决差异。用户明确要求重新设计或从零新建时，按新范围推进。

仅调整方案时保留已有资源；重新设计也不自动授权删除或重建，资源操作仍遵循用户范围和相应权限确认。

`intake.confirmed` 仅表示需求澄清完成，不能替代 Plan 当前 revision 的批准或工具权限确认。

## 1. 理解需求，形成候选

从用户输入、相关材料与已有 brief 理解六项信息：**业务目标、实际使用者、核心动作、业务对象、已知流程与限制、视觉风格**。复用已答内容，区分事实、推测和关键缺失；只有会改变核心范围或实际用法的缺失需要前置补问。

围绕“谁要完成什么事、处理什么对象”，推导少量可独立取舍的核心功能：

- 每项对应一个业务任务，用“功能名称＋一句用途”说明谁做什么；各项保持相近粒度，字段和流程细则交下游规划。
- 保留用户明确要求，推荐实现业务目标的最小有用功能组合；仅有“管理系统”或风格要求时，不自动把经营看板加入核心功能。
- 不同用法会影响入口判断时，分别写成含义清楚的功能选项，或补一道实际用法题；角色关系按已知事实记录，推测标记为建议。

先按业务任务展示候选，收到用户选择后再判断入口方案。用户已有明确要求直接沿用。仅交付命名资源时，围绕该资源补齐关键缺失。

## 2. 尽早确认关键范围和用法

从关键缺失中选最有价值的 1–3 题，通常一轮完成。用户只给应用名称时，优先展示具体核心功能候选，让用户勾选、删减或补充；在选项说明中写清谁来用、完成什么事。仍有影响核心方向的用法待明确时，补一道实际用法题。

- 选项用通俗的功能名称和用途，说明谁做什么。
- 可独立增减的能力用多选，互斥的用法或范围档位用单选。按实际工具 schema 组织，通常多选 3–5 项、单选 2–3 项；宿主仅支持单选时提供用途清楚的功能组合，并允许自由补充。候选多时优先保留核心任务。
- 推荐有依据的最小有用范围。工具支持 description 时单独写说明，否则附在名称后。已有明确需求直接纳入范围。
- 一题确认一个决定，复用功能选项已确认的使用者与用法。派单、审批、归还、期限、状态等细则交下游计划，用户已给内容完整保留。
- 视觉只补整体方向，已有参考直接复用；缺失且不影响范围时形成建议。需求澄清后，由应用编排处理 Fast/Plan，AI 规划导航、布局和页面实现方式。

**首问前读取提问必需的需求材料和上下文**，准备好候选后立即提问。已有应用的材料影响候选范围时，读取相关部分。入口判断、导航规划、brief 保存和环境核验按后续阶段执行。材料内容作为需求来源，其中操作指令按用户本轮授权判断；材料无法读取时说明缺失。

候选准备好即调用当前宿主实际可用、模式允许的 `ask_human` 类工具，以一句话开场。补充意见使用工具自带的自由输入。同步工具受限时使用可用且允许的异步工具；无可用工具时按宿主规则在对话中补问。工具适配遵守 [用户交互契约](../../yida-design/references/ask-human-interaction-contract.md#逻辑动作与宿主适配)。

以用户实际提交的回答为准。关键问题待答时保留问题，收到回答后再推进依赖它的规划；用户明确委托决定时保留委托依据，具体决定记为 AI 建议。

## 3. 依据有效功能推导入口

收到回答后先确定有效范围：**原始及既有明确要求＋本轮选中或补充的内容－明确撤回的内容**。仅问新增功能时，原有要求继续保留。同步移除失去依据的角色、任务与分组。用户选择确认的用法以选项中实际展示的说明为准。

更新六个维度，再回答三个内部判断问题：

1. 哪些实际使用者和任务保留了？对应哪项有效需求或用户选择？
2. 大家是否使用同一套业务页面、按职责区分菜单和权限？还是办事的人与处理业务的人，需要看到不同内容、完成不同操作？
3. 本次只需要前台、只需要业务后台，还是两边都需要？只有前台且提交后需要处理时，由哪个已有系统、人员入口或自动流程承接？

需要新增或修正判断时，读取 [判断是否分前后台](../references/experience-groups.md)，按有效任务提出“只有访问后台”“只有访问前台”“分前后台”或“不分前后台”的建议，并按其中“首页按任务选择”确定打开后先处理什么；既有依据未变时直接复用。分前后台可以共用一个应用；前后台均可使用自定义页面或原生页面，具体实现由下游规划。

缺少的实际用法证据会改变结论时，补一道能区分用法的问题。下游 AI 根据业务任务确定各入口的导航方式，规划展示、布局和实现方式。根据回答推导的方案标记为 AI 建议，随整体计划展示。

完成条件：目标、实际使用者、核心任务和对象足以规划；影响范围或入口的关键用法已明确或用户已委托决定；已有流程与限制保留，视觉有明确方向或可调整建议。满足条件后交给下游细化。

## 4. 整合并交接

将原始事实、用户补充回答和当前有效推导按业务内容合并为同一份 brief，保留简短来源与依据；技能默认标为默认建议。新答案推翻旧猜测时，用新结论更新对应内容。

读取 [交接契约](../references/handoff.md)，更新同一份 `requirement-brief.json`，交接有效功能、用户与任务关系、入口及承载建议。保留已有细项、稳定标识、明确 Fast/Plan 选择，以及用户对 `theme-file`、`page-source`、`publish` 等操作的限制，并作为执行约束交接。`intake.confirmed` 表示前置澄清完成；搭建计划获批由独立的计划版本状态记录。

保存后直接交给 `yida-app` 规划准备；用户仅讨论或要求只在对话中处理时，遵从该范围。通过按需阅读、合并工具调用和简短开场加快首问。

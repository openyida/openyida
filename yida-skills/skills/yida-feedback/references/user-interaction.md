# 面向技术小白的反馈引导

用户只描述问题，Agent 负责诊断、写材料、准备公开修复和运行验证。不要让用户选择仓库、输入 Git 命令、找源码、填写技术 JSON 或自行撰写 Issue/PR。Git/gh 缺失时优先使用宿主现有的 GitHub 连接器/浏览器；不要把安装研发工具当成向用户反馈问题的门槛。

## 一、先解决“我想反馈什么”

复用当前对话，只补关键缺口。给用户三个容易理解的入口：“遇到问题了”“希望体验更好”“想一起改进”。询问“你原本想完成什么？实际发生了什么？你希望看到什么结果？”；已知答案直接复用，不一次追问整张技术表。Agent 整理最短复现、影响和真实排查结果，缺失项写未知。体验建议用现有 `summary/actual/expected` 表达当前场景、不便和理想结果，不要求用户设计命令或先找到根因。

环境信息按 [报告输入](report-input.md) 填写：只读检查可获得的 OpenYida、Node.js、系统和架构，复用已知的 AI 工具及版本、安装方式；浏览器、设备、公有云/私有化和多组织切换仅在相关时补充。只将确认属于问题发生时的值写入 `incidentEnvironment`。已升级或换机器时分开记录，不用当前版本覆盖历史事实；未知不阻塞反馈，不要求粘贴整份诊断。

说明下一步：“我会先整理问题和截图，再给你确认；确认后才公开提交。”不要先要求注册账号或下载源码来打断排查。

能使用宿主 `ask_human` 时，使用结构化问答；没有时使用宿主等效的用户提问工具或普通对话，不模拟不存在的工具。普通本地会话不能调用受管专用 `openyida agent ask-human`。只有工作区 AGENTS.md 明确声明 managed Run 时，才按根技能的该命令契约写问题 JSON、提交并在 queued 后结束本轮，等待续接答案；不能把该命令当成普通 CLI 通用问答。

## 二、准备复现截图和材料

- 优先复用用户在当前会话明确提供的截图。需要新截图时，可使用宿主浏览器工具捕获用户允许复现的页面，或请用户通过宿主附件入口提供；不扫描相册、桌面或其他会话。只支持文本的问答工具不能接收图片，不能要求它上传截图。
- 只保留能说明复现步骤和错误的最少图片。检查截图中的姓名、头像、客户数据、地址栏、组织信息及可能的隐藏个人信息；需要遮挡时先让用户提供脱敏版本，不能用生成图片伪造或补造故障证据。
- 输入摘要的 `screenshots` 只列用户已选择的本地图片路径和用途，报告命令会复制这些原图到私有本地目录并使用通用文件名，不联网、不修改图片、不保证清除图片元数据。路径仅供本地读取，不进入公开报告。
- 没有截图时先说明缺什么，帮助用户补充。终端故障可提供脱敏报错文本；无法补图时，让用户明确选择“先提交现有文字”或“补图后再提交”，在正文注明未提供截图，不冒充已有图片。
- PR 必须另准备修复前后测试对比：用户安装版本/公开基线、修复版本、同一最小复现或测试命令、前后实际输出与证据、回归结果及未验证范围。填写 `comparison`；未运行写 `not_run`，不得编造“修复前失败/修复后通过”。尚不能验证时明确说明，优先建议 Issue；用户仍选择草稿 PR 时，比较报告也必须如实保留未运行和原因。

## 三、先让用户看懂将公开什么

展示一份可读的最终预览，包含：

1. 提交到哪里：公开 OpenYida 仓库的 Issue，或个人 Fork → 上游的草稿 PR。
2. 最终标题、正文；PR 同时包含修复摘要和测试对比报告。
3. 所有拟上传截图的实际预览、说明和数量；不能只展示本机文件路径。
4. 明确提示：“提交后这些文字和截图会公开。请检查是否含敏感信息，或有你不想公开的内容。”

正文可使用宿主可访问的文档/预览链接，图片用宿主支持的图片预览。不要把本机路径当成远端可访问链接，不要先上传到 GitHub 或公开图床再让用户确认。受管问答附件只支持指定的 HTML/Markdown/文本，不可把二进制图片塞入附件；图片另用宿主支持的预览能力，确认要绑定同一份正文和截图。无法展示图片时，先协助用户检查已提供的脱敏版本或明确选择不提交该附件，不能将看不到的附件混入公开确认。

然后通过 `ask_human` 或宿主等效工具询问：

> 请检查上面的文字和截图：有没有敏感信息，或你不想公开的内容？
>
> 选项：
> - 已检查，可以按这份内容公开提交
> - 先删掉或修改一些内容
> - 暂不提交

允许自由补充要删的段落、字段、截图或测试细节。取消就保留本地草稿；要求修改时，Agent 执行删除/改写后重新展示最终稿并取得确认。不能把先前的“帮我提 Issue/PR”当成对尚未见过的内容的隐私确认，也不能使用默认选中项代替用户回答。

将确认绑定到具体正文、截图内容和测试报告。报告输出的 `reviewDigest` 根据实际正文和图片字节生成，供 Agent 在内部记录确认版本；`fingerprint` 只用于问题查重，不能作为同一公开稿的证明。发送前重新核对正文和附件未变化，不把哈希或技术参数作为用户操作步骤。确认后任何正文/图片新增或变更都须重新确认；只对外提交用户最终批准的部分。提交时只引用审阅后的文件，不使用原始摘要、原始截图或整份日志。用户要求删除测试敏感明细时，保留其同意公开的脱敏前后结果；如不愿公开任何测试对比，改为 Issue 或暂不提交 PR，不恢复用户删掉的内容。Issue/PR、附件上传的授权与最终内容确认可以在同一次问题中取得，不重复索要相同确认。

## 四、账号与提交结果

- 材料准备好、用户选择 GitHub 后，按 [账号与工具准备](github-setup.md) 区分没有账号、工具未安装、未登录和权限/网络问题。先复用已有工具；推荐 CLI 时先执行只读 `feedback github setup --json`，说明安装计划并取得同意后才使用 `--install --confirm`。注册、登录由用户在官方页面或宿主安全入口完成，配置完成后继续原草稿。
- 实在不行，只提示“反馈到AI开发者群”，附本地脱敏报告供用户自行反馈；不再索要群信息、不编造群链接、不替用户发送消息。
- 用户愿意用 GitHub：Agent 按 [GitHub 提交](github-contribution.md) 查重、处理公开代码和 Fork、提交已确认材料。gh 缺失或不支持附件时，使用宿主可操作的 GitHub 网页引导，不要求用户记技术命令；无法完成时交付可粘贴的正文及已检查截图，不默默省略附件。
- 成功后给可点击的 Issue/PR 链接，读回核对正文和截图是否完整。附件上传失败或结果未知时先查已创建的帖子，说明实际完成部分，不重复建帖。没有核实的 URL 时，只能说“草稿已准备”。

## 五、Issue 成功后，邀请一起改进

仅在 Issue 创建成功且读回完整后，给一次可选邀请；失败、仅有草稿或附件缺失时先处理提交结果。若读回已有仓库欢迎评论中的 PR 邀请，直接引用它，不再追加第二段邀请。用户已拒绝贡献时跳过，不追问理由。复用同一会话的问题和环境，不重新做一次问卷。

> 问题已提交：[Issue 链接]，感谢你帮我们发现它！
> 如果你愿意，我们还可以一起尝试修复，并提交一份修改建议（PR）。不需要你会 Git 或写代码，AI 会协助准备修改和检查，你确认后才公开提交。只反馈问题也完全可以。

选项：“让 AI 试着修复”“先看看需要改什么”“只反馈问题”。用户未回答时保持 Issue 已提交状态，不默认开始代码工作。

- 让 AI 试着修复：在公开代码中尝试定位、准备最小改动和验证；找到真实修复后按 PR 流程展示 diff 与最终稿，再确认远端操作。
- 先看看需要改什么：只读分析，解释预计改动、风险和验证方式；等用户选择继续再编辑。
- 只反馈问题：交付链接并结束，不再推荐 Star、Fork 或 PR。

有关联 Issue 时在 PR 中引用；只有确实解决问题才写 `Closes #编号`。原因不明、平台内部限制或无法找到公开修复点时，补充 Issue 材料与限制，不制造无关 PR。文档和 Skill 的小改进同样欢迎，验证按改动类型安排；本地检查通过不代表平台、浏览器或真机已验证。

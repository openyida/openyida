# 账号与工具准备

用户选择 GitHub 提交或贡献后读取。先保留已有问题、环境、草稿、截图和测试结果，再准备账号与工具；整理反馈本身不需要账号或安装工具。下面的检查与命令由 Agent 执行，给用户说明用途和下一步即可。

## 1. 分清账号、工具和权限

先复用用户已说明的账号情况和宿主已授权的 GitHub 连接器/MCP、可操作浏览器。选择本机 CLI 路径时，由 Agent 执行 `openyida feedback github setup --json`，只读检测 gh 与当前账号，不安装、不登录，也不查询 Star/Fork。只检查当前任务所需能力，不遍历账号配置、环境变量或凭证文件。

| 观察到的情况 | 怎么引导 |
| --- | --- |
| 用户明确说没有账号 | 给 [GitHub 官方注册入口](https://github.com/signup)，由用户自行注册、登录；不愿注册就保留脱敏报告 |
| `gh` 不存在 | 仅说明本机未安装该工具；账号是否存在仍未知，继续检查已有连接器或网页路径 |
| 有工具，但登录未验证 | 先确认用户愿意使用该工具，再引导官方登录；不把工具未登录说成用户没有账号 |
| 请求超时、限流、权限不足 | 说明具体阻塞，保留账号/Fork 状态为未知；不反复要求注册、安装或切换账号 |
| 已登录且具备所需能力 | 复用当前工具；多账号或不同工具身份不一致时，让用户确认用于本次贡献的账号 |

`openyida feedback github status --json` 仍只用于原流程需要的个人 Fork/支持状态检查，不作为每次 Issue 的前置。它依赖本机 gh，`gh_unavailable` 表示工具缺失，`account_unverified` 表示账号未验证；两者都不能证明用户没有 GitHub 账号，也不能否定浏览器/MCP 已登录。

无账号时可这样说：

> 问题和环境信息已经整理好了。公开提交到 GitHub 需要一个账号，我可以引导你完成注册和登录，你在官方页面操作即可。现在不想注册也没关系，反馈材料会保留下来。

账号密码、验证码和 Token 只由用户在官方页面或宿主安全授权界面处理；不向用户索取，也不读取、输出或写入报告。无法使用 GitHub 时按[用户交互](user-interaction.md#四账号与提交结果)交付本地报告。

## 2. 选择最省事的可用路径

用户选目标，Agent 选工具；不要求小白判断 CLI 和 MCP 的区别。

| 当前目标与条件 | 推荐路径 |
| --- | --- |
| 已有工具已授权且能完成当前操作 | 直接复用；Issue 需要查重、创建和读回，PR 还需要核验个人 Fork、准备分支改动及创建和读回 PR |
| 希望 AI 协助提交反馈/需求，缺少工具且宿主支持终端 | 推荐 GitHub CLI，先用 setup 检测并展示安装计划，再征求同意；不想安装或只提一次 Issue 时可直接使用网页，无需 Git 或源码 |
| 希望 AI 协助修复并提 PR，宿主支持终端 | 缺少必要工具时，经用户同意后协助配置官方 GitHub CLI；Git、依赖安装及本地测试能力按实际需要单独核实 |
| 宿主已有方便的 GitHub 连接入口 | 经用户同意连接官方 GitHub MCP/连接器；只在宿主实际支持时推荐，不虚构入口或配置 |
| 无法安装、连接或使用终端 | 使用可用网页能力；无法编辑或验证时保留草稿、修改成果和未验证说明，不宣称已提交或测试通过 |

MCP 配置在用户当前使用的 AI 工具中，不是新增 OpenYida 命令。已连接不等于具备写权限；只读连接可用于查重，不能冒充可提交。也不把 GitHub MCP 或 gh 当作本地 Git、构建和测试环境的替代品。

## 3. 需要配置时，先说明再执行

结合实际环境，推荐一个具体选项，说明工具名称、官方来源、包管理器默认安装位置及必要依赖、用途和所需授权。复用已安装的包管理器和已有宿主配置；需要额外工具时另行说明并征求同意，不扩大原安装授权。

> 目前还没有可用的 GitHub 提交工具。我建议配置官方 GitHub CLI，方便我协助你准备修改和提交 PR；它会安装到你的电脑，登录授权由你在浏览器中完成。提交前，我仍会先给你看修改和将公开的内容。
>
> 选项：“帮我配置并继续”“使用网页方式”“先保留成果，稍后继续”。

这是 CLI 路径的话术；推荐宿主连接器时，改为真实的连接名称、授权范围和配置位置。用户明确同意后才开始安装或修改配置；拒绝或未回答时保留成果，不自动代选、不反复邀请。

- **GitHub CLI 检测与安装**：先运行下方只读命令，按返回的 `tool/account/installation/nextStep` 解释当前状态。缺少 gh 且 `installation.plan.available` 为 true 时，向用户展示具体包管理器、包名、安装影响和协议；用户同意后才运行安装命令。macOS/Linux 复用已有 Homebrew，安装 `homebrew/core/gh`；Windows 复用已有 WinGet 的 `winget` 源，安装精确包 `GitHub.cli`，会接受来源与软件协议，系统权限由用户自己批准。已有 gh 直接复用，不升级。没有支持的包管理器时提供[官方安装说明](https://github.com/cli/cli#installation)或网页路径；命令不安装包管理器、不加软件源、不执行提权或远程脚本。
- **浏览器授权**：setup 仅提供引导，不自动启动登录。用户同意登录后，Agent 在用户可见的交互终端运行 `gh auth login --hostname github.com --web --skip-ssh-key`，由用户在官方浏览器页面完成。无交互终端则选网页/安全连接器，不在后台挂起登录。不要替用户回答 Git 凭证配置或协议切换问题，不自动修改全局 Git 配置、添加 SSH key 或追加权限；OAuth 权限以实际授权页为准，不能把 `--scopes` 描述为只读/写入权限开关。若安全存储不可用，gh 可能回退为明文保存；提前说明风险，优先选择网页或宿主安全授权，不使用 `--insecure-storage`，也不读取或回传凭证文件。
- **宿主 MCP/连接器**：读取当前宿主的连接说明及 [GitHub 官方 MCP 文档](https://github.com/github/github-mcp-server)，使用实际提供的连接/授权入口。优先使用宿主支持的浏览器授权，只申请本次操作需要的权限；若只能手填 Token，由用户在安全设置中自行填写，不通过对话传递。修改配置只改已同意的 GitHub 项，保留其他连接；不顺带安装本地服务或覆盖整份配置。
- **受限环境**：遵守宿主权限和受管 Run 约束；受管环境不能使用个人 GitHub 能力时，交付脱敏草稿并说明到个人本机会话继续。不以换成浏览器/MCP、提权、关闭安全检查或扩大权限来绕过限制。

安装、登录或连接失败时说明实际完成到哪一步，保留材料，提供网页或稍后继续的选择；用户未选择重试时停止配置。配置授权只覆盖说明过的安装/连接，不等于授权 Star、Fork、push、Issue/PR 提交或公开内容。

以下命令由 Agent 执行；`--confirm` 只记录用户已明确同意安装，不代替对话确认：

```bash
openyida feedback github setup --json
# 用户看过安装计划并同意后：
openyida feedback github setup --install --confirm --json
```

仅 `tool.state=missing` 才可安装；`unverified` 先检查执行权限或环境。账号的 `login_required` 进入登录引导，`unverified` 先检查网络、授权或限流，不要求重装/重复注册。安装超时、失败或结束后仍找不到 gh 时，先用只读 setup、包管理器状态或重新打开终端核实 PATH；不把包管理器退出成功当成工具就绪，也不自动重试。所有 setup 输出仅供本机引导，不直接附到 Issue。

## 4. 验证后接着处理原草稿

1. **只读验证**：CLI 再运行 `openyida feedback github setup --json`；它用固定 github.com 的只读 API 核实当前用户，仅返回验证后的账号名，不输出原始诊断或凭证。必要时检查 `gh auth status --hostname github.com`，不使用 `--show-token` 或 `gh auth token`。MCP/连接器读取当前用户和可用工具，浏览器核对登录账号。账号验证不代表有写权限；所需权限尚未证实时标为待验证，不创建测试 Issue、Star 或 Fork 来试权限。
2. **复用已有材料**：继续原问题、出错环境、草稿、截图及测试记录，不重新问一遍。仅因安装 gh 或登录成功，不修改 `incidentEnvironment`，也不把新安装信息加入原问题报告。账号、授权输出和工具配置不写入公开材料。
3. **保留公开确认**：未改动的最终稿沿用原确认；正文、图片、diff 或测试结果有变动时重新展示并确认。安装成功、登录成功和工具就绪，都不代表用户已同意公开提交。
4. **按原提交流程继续**：回到 [GitHub 提交](github-contribution.md)，核实目标仓库与账号；PR 仍通过已验证的个人 Fork。若中断前提交结果未知，先查询已有 Issue/PR/分支，避免重复创建。结果仍未知就保留待核实状态，不换工具盲目重发。
5. **如实交付**：分别说明“工具已配置”“登录已验证”“草稿已准备”或“已提交并读回”。只有核实真实 Issue/PR 地址和内容后，才给提交成功结论；Issue 完整读回后的可选 PR 邀请沿用交互规范，不因配置工具重复邀请。

官方参考：[CLI 登录](https://cli.github.com/manual/gh_auth_login)、[登录状态](https://cli.github.com/manual/gh_auth_status)。

# 前端资源创建与部署引导

本指南把插件源码、构建和资源托管分开。推荐顺序是：**已有企业静态资源服务器/发布流程 → 码云 + 阿里云 OSS → GitHub Actions + Pages 备选**。集团开发者优先沿用已授权的内网仓库及资源发布渠道，不把集团代码移到外部仓库。

本指南是操作方案，尚未完成这些渠道的宜搭真实加载验收。用户只要求指导或明确暂不测试时，只讲解、准备本地文件；不运行构建、HEAD 探测、流水线或部署，不把测试作为隐含步骤执行。

## 先确认当前缺什么

先问一个问题：“你们是否已有可以发布 JS 文件的企业静态资源服务器、HTTPS 域名或 CDN？”

- **有**：确认发布负责人、可写目录、目标用户可达的 HTTPS 基址，走下一节，不另建仓库或 OSS。
- **没有**：说明国内默认方案“码云管理源码，阿里云 OSS 提供资源地址”，再询问是否已有代码仓库、阿里云账号与可用域名。已有仓库可以保留，码云不是 OSS 的强制前提。
- **尚未开通插件开发权限**：先按 Skill 的插件共创申请入口引导；开发权限与 OSS 托管权限分别处理。

每一步都说明“入口、要填什么、完成后给我什么”。用户需要手动操作时，打开对应官方页面并停在操作位置；没有页面打开能力时给可点击链接。账号登录、实名、协议、支付、仓库可见性与公开访问由用户确认，不索要聊天中的 AccessKey/密码。资源创建、上传和发布必须在用户选定目标并授权后执行。

## 已有企业服务器：直接复用

1. 请用户或管理员提供现有发布流程、HTTPS 资源基址及允许的目录，不要求提供服务器密码。集团环境使用现有 DEF/云构建等已授权渠道返回的真实地址，不编造 `g.alicdn.com` group。
2. 建议按插件和版本隔离目录，如 `plugins/calendar/1.0.0/`。确认容器名、扩展点导出、publicPath 与实际宿主匹配，细节见[开发规范](./development-guide.md#第三方前端配置与构建契约)。
3. 获准后按项目真实构建命令生成并发布整个产物目录，包含 `remoteEntry.js`、chunks、CSS 和所需媒体；不要只上传入口文件，也不要覆盖其他插件或旧版本资源。
4. 请发布负责人给出稳定的完整 HTTPS 入口。需要登录门户、短期签名或 VPN 的地址不能未经确认就作为所有目标用户可加载的资源。

## 没有现成资源：码云 + 阿里云 OSS

### 1. 创建或复用代码仓库

- 入口：[Gitee](https://gitee.com/)，官方操作参考：[仓库创建入口说明](https://gitee.com/help/articles/4348?skip_mobile=true)。用户登录后进入新建仓库，核对归属个人/企业、名称、路径和可见性；未要求开源时建议私有，不擅自公开。
- 已有源码仓库就继续使用，不自动换 remote 或迁移；新建时也只在确认归属和权限后关联仓库。源码中排除登录缓存、备份、密钥、内部业务数据及不允许外发的依赖；不要把整个 OpenYida 工作区推到插件示例仓库。
- 完成后请用户提供仓库地址与目标分支。码云负责版本管理，不能把仓库文件链接填成宜搭脚本路径；[Gitee 官方反馈](https://gitee.com/oschina/git-osc/issues/I9QF16)说明 Pages 服务已下线。

### 2. 准备 OSS 存储空间和稳定域名

- 入口：[阿里云 OSS 控制台](https://oss.console.aliyun.com/)，按[创建 Bucket 与上传文件教程](https://help.aliyun.com/zh/oss/user-guide/get-started-with-oss/)操作。先确认账号归属、地域和存储/请求/流量费用，由用户确认预算与开通，不承诺免费。
- 有专用于公开前端资源的 Bucket 就复用允许的目录；否则创建专用 Bucket，避免与业务数据混放。初始保留私有权限，先明确对外读方案：只让待交付的静态产物可读、上传仍须授权；不要把整个业务 Bucket 改成公共读，更不能公共读写。可以由管理员配置限定目录读取，或采用私有 OSS 源站配合获准的 CDN 回源方案。
- 域名按[OSS 自定义域名说明](https://help.aliyun.com/zh/oss/manage-a-domain/)绑定，配置 DNS 与 HTTPS 证书。中国内地 Bucket 绑定域名需按云服务要求完成备案，不能承诺开通即刻可用。缺少域名或配置权限时，明确让用户/管理员提供域名及协助，不用临时签名下载地址冒充长期入口。
- 只有 JS/chunks 文件交付时不必为了插件配置网站首页。CDN 可按目标网络、流量和预算后续添加，不强制购买。完成后记录实际 Bucket、地域、允许的目录前缀和 HTTPS 基址；这些信息不是上传密钥。

### 3. 构建并上传完整产物（获得执行授权后）

- 先检查真实 `package.json`、锁文件、Node 版本和构建配置，再给出适合该项目的安装/构建命令；有 npm 锁文件且定义了 build 时可用 `npm ci`、`npm run build`。不要假设每个项目都用同一构建器或输出目录。
- 构建契约来自开发规范：Module Federation 容器名须匹配插件 UUID/当前宿主规则，输出 `remoteEntry.js`，暴露正确场景模块，并正确设置 publicPath。
- 小规模首次交付可指导用户在 OSS 控制台把整个构建产物上传到专属版本目录；保留相对目录结构，不上传源码、配置备份、凭据或未经审查的 source map。后续再按用户需要使用获准的 Gitee 流水线或企业 CI 自动构建上传，不把“创建仓库”当作触发流水线的授权。
- 上传身份只授予目标 Bucket/前缀所需权限，凭据放云服务/CI 的受保护凭据配置，不写入前端包、仓库或对话。
- JS 应返回正确的 JavaScript Content-Type；若实际宿主加载方式需要 CORS，按真实页面 Origin 配置读取所需的方法/头，不为静态读取开放上传权限。缺失的 chunk 必须返回真实错误，不通过 SPA fallback 把所有 404 改成 HTML 200。
- 使用版本目录保留旧版本；不要覆盖正在被其他组织使用的路径。最终交付的是类似 `https://<实际资源域名>/plugins/calendar/1.0.0/remoteEntry.js` 的完整地址，不能凭示例域名生成一个“已发布”地址。

### 4. 接回宜搭 CLI

资源地址准备好且获准保存后：核对目标组织和登录态 → `plugin version-get` 获取完整配置及 snapshotHash → 仅替换 `frontEndDevInfo.cdnEntry` → `plugin save-dev` 带备份和原摘要保存 → 回读核对。不要把其他两段配置丢掉或误传为空对象。

具体命令见 [Skill](../SKILL.md#开发与版本配置)。`plugin probe` 输出的 `hostingGuide` 指向本指南；不带 `--check-resource` 不请求资源地址，带该参数也只做 HEAD、不部署。平台 API 查询仍需要登录，不能把 probe 说成完全离线工具。

若用户授权验收，再逐层检查资源与依赖、运行时候选、官方发布状态及真实消费者；否则记录“已准备/已保存，尚未验证加载”，不自动测试或发布到组织。

## GitHub 备选方案

用户已有 GitHub 工作流、主要面向海外，或明确选择该方案时再建议 Actions 构建 + Pages 托管；仍不把 GitHub 设为国内默认。步骤是：确认仓库可见性和可外发内容 → 按真实项目准备构建工作流 → 将完整产物交给 Pages → 使用实际部署返回的 HTTPS 入口。具体可用性、权限与设置以 [GitHub Pages 官方文档](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)为准。

用户只选方案时可以准备本地工作流草案，不能擅自创建仓库、push 或触发 Actions。GitHub 仓库首页、blob/raw 链接不作为默认生产资源渠道；部署方案本身不等于宜搭加载验收通过。

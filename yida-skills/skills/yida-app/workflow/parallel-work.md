# 并行执行

Fast 完整应用直接沿用已确认事实和范围，按 yida-app 的 [Fast 直接搭建](fast-build.md) 立即创建/复用应用并独立生成 app_theme.css，不等待完整 JSON、requirement-brief、PRD 或 design.md；下方文件输出约定用于 Plan/已有文档任务。需求确认、禁止项、实际并行能力与验收要求不变。


## 可以同时做什么

| 阶段 | 可并行任务 | 何时进入下一步 |
| --- | --- | --- |
| 需求分析 | 读取互不依赖的附件、已知资源与品牌资料 | 汇总事实后，统一询问未决事项 |
| 需求确认后 | 业务对象、字段、流程与页面规划；基础主题、配色、token 与素材策略 | 页面任务和区块确定后，补齐各页设计 |
| 计划或主题确认后 | 立即生成主题 CSS（Plan 已有 outputs.theme 时直接复用）；按已确认业务创建应用、表单并编写页面 | CSS 不依赖 appType 或表单；应用就绪后即可创建表单；appType 与 CSS 都就绪就立即更新主题设置 |
| 图片要求就绪（Plan 已确认） | 搜图与创建应用、表单、页面同时推进；有图页面先做布局和交互，同页各图片位置并发搜索 | 每页草稿就绪即检查直链；上传时使用真实 appType；图片只在所属页面接图和验收时汇合 |
| 表单创建 | 无依赖表单通过 `create-form batch` 同时创建、回读 | 关联表单和真实字段就绪后创建依赖表单；全部页面开发并发布完成后由主流程统一导航排序 |
| 页面创建或复用后 | 取得 formUuid 后仅为已规划独立入口或应用级自绘导航的页面隐藏导航并回读；平台导航管理页保留导航，同时编写业务内容 | 代码开发不等待配置请求，发布后核对 renderNav 未被改变 |
| 页面实现 | 无直接依赖的页面同时开发、编译和检查，各自就绪后发布 | 每页只等待自身所需的真实资源；全部页面完成后统一排序与最终验收 |
| 发布后 | 独立页面的只读配置与数据回读 | 主流程汇总结果，再完成应用级验收 |

首次搭建的必要确认完成后，才启动业务与视觉规划。Plan 还需用户确认当前方案，才能创建和发布资源。

## 主题与业务资源的依赖

- 用户确认计划或主题，且主色、导航明暗与相关 token 已确定，即可开始生成应用主题 CSS；不等待表单字段、页面源码或页面发布。已有符合当前确认版本的 CSS 直接复用。
- 取得真实 `appType` 后，表单创建与主题生成/上传并行；页面按已确认的设计和 token 契约开发，不等待主题上传结束。业务资源仍遵守已有的方案确认和资源创建条件。
- 先按 [旧主题注入与停用规则](../../yida-design/references/application-style-library.md#旧主题应用的样式作用域与确认) 核对服务端主题能力；旧主题或能力未知时优先使用页面局部样式，未取得目标应用与 CSS 范围的明确注入确认不得上传。符合注入条件且 `appType + 当前已确认的 CSS + 已确定的导航配置` 就绪后，立即执行一次 `update-app --theme-file`，同步 `colour=custom`、从 CSS 提取的 `themeColor`、`customThemeStyle`、`navTheme`、`layoutDirection`、Logo 来源及导航显隐。其中已确认的应用导航隐藏通过 `--hide-app-nav` 同步保存，不等待页面创建或开发完成。页面级隐藏仅用于已规划独立入口或应用级自绘导航的页面，取得其真实 `formUuid` 后执行 `update-form-config` 并回读；平台导航管理页保留导航，不加入隐藏队列。配置可与源码开发并行。
- 同一应用的基础设置由主流程单一任务写入；主题上传、导航配置和其他设置更新不能并发覆盖。表单/页面资源的独立写入可继续并行。
- 生成 CSS 的任务独占主题文件；上传使用已完整写入的版本，不上传仍在修改的文件。主题确认内容变化后，只重做受影响的 CSS 和设置同步，不让旧任务覆盖新版本。
- 主题同步失败只重试主题分支，其他资源开发继续；视觉验收与最终交付必须汇合 `themeVerification.verified=true` 的结果，不能在主题未生效时报告视觉完成。不要把汇合检查误作“到收尾时才开始更新主题”。

平台导航排序是所有页面开发、发布和资源创建后的汇合任务，不与它们并行；每个页面发布时不附带 `--auto-nav-order`，主流程最后按 PRD 执行一次 `order`；用户明确要求自动整理时才用 `auto-order`。自定义导航的菜单顺序与默认页在页面开发时实现，发布后核对实际入口。应用主题更新和页面导航隐藏仍按前述时机提前执行，不随排序一起推迟。

## 素材与页面同时推进

整次图片采集默认共用60秒，不为每个页面重新计时；单次搜索最多15秒。各素材任务沿用同一个 `collectionDeadlineAt`，`asset resolve` 追加 `--deadline-at <同一ISO时间>`。403/429等受限来源立即停用并换源，不使用 `sleep` 退避。装修官网等展示页先完成页面、案例筛选与详情和移动布局，缺图时明确展示缺图或示例状态，图片到位只更新绑定。预算耗尽后记录缺口并收口，不等待整个素材任务包。

1. Plan 当前方案确认后，先核实宿主 background_agent/background_shell 和实际工具参数，再按物化结果 `assetTasks[].executionContract` 选择真后台 Agent、后台 Bash 或业务优先同步批次；Fast 在需要的页面使用携带 assetStrategy 的素材草稿，通过 --input 建立同样任务，不需要业务上下文。按 [后台启动与接收](../../yida-image-assets/SKILL.md#后台启动与接收) 记录真实任务编号、页面、输出和截止时间，复用已有任务。后台派发成功后主流程立即继续创建应用、表单和页面。只有同步 Agent 时禁止整包素材前置：先做已授权资源创建/复用、范围内种子、无图页面及图页布局，再分批素材。QwenWork 若实际 Bash 支持 run_in_background，则用于可脚本化步骤；看图判断仍使用可看图的工具。
2. 同页的各图片位置也是独立搜索任务。按宿主允许的并发能力同时发起，整次采集共用最多四个在途搜索，完成一个就补下一个；批量调用需实际同时发出请求。每个位置仍只选一张图，最多两轮。只有串行工具时按位置执行并记录限制。
3. 任务先读取已有页面清单，复用符合当前用途与尺寸要求的 final 图片，继续剩余位置和轮次。搜索任务返回选图及来源信息，由该页唯一写入者组装草稿。每页使用 `assetTasks` 返回的 draft/manifest 路径；草稿就绪即执行 resolve.argv；需要上传时追加 uploadArgs，并填入真实 appType。页内图片由 CLI 并发检查，允许外链就直接交付，需托管时再上传。
4. 所有页面先做布局、文字、真实数据绑定和交互，就绪即按已有发布授权提供首版预览。图片未齐采用设计允许的明确缺图状态；预览后才汇合素材，已验证图片只更新绑定并核对裁切和清晰度，不重新生成页面。缺必需图时保留最终验收缺口。
5. 记录工具名、后台参数、真实任务编号、派发返回时间，以及素材与业务任务的开始/结束时间；开始早于素材结束不足以证明并行，还需区间确实相交。收尾把 assetTasks、taskState 和 businessWork 汇总进 build-manifest，check-prd-completeness 会标记证据缺失、伪后台或同步路径素材前置为 needs_review。资源或宿主限制记录具体原因；仅回读记录不等于独立核实宿主执行。

## 页面按实际依赖并行

- 根据 PRD 为每个页面列出自身需要的表单/字段、目标页面 ID、共享组件契约和独占源码路径。没有直接依赖的页面同时开发，不按菜单顺序或“先首页、再列表、最后详情”逐页等待。
- 共用已确认的主题、导航数据契约或已就绪表单，不构成页面间串行依赖；共享输入只读复用。仅跳转到另一页面时通常只依赖目标页面 ID，不必等待目标页面的代码完成。
- 某页需要的真实字段、流程或接口未就绪，只等待该页受影响的数据绑定或联调；其余页面继续开发。可先完成该页不依赖资源的布局与交互，不用假 ID 或 mock 数据冒充完成。
- 每页使用独立源码、page-spec、本地编译输出和发布目标；同一页面不可被两个任务同时修改或发布。共享导航/组件由一个任务维护接口，其余页面按契约接入，不互相覆盖。
- 每页独立通过本地检查且其真实依赖就绪后即可发布、回读，不要求先等所有页面源码完成。某页失败只重试该页及依赖它的工作；全部页面和资源完成后再统一导航排序及应用验收。

## 调度方式

先消费 `agent-capabilities --summary-json` 的 `task_execution`，再按任务性质选择执行方式；任务并发、子 Agent 委派和后台执行分别核实。

- 输入和资源 ID 已就绪的独立 CLI 工作，按命令清单的 `task_concurrency` 分批。普通运行用 `openyida batch ready-tasks.txt --concurrency 3 --json`，一行一条完整命令；未指定时仍串行。已审计的只读任务和不同页面的 compile/publish 可重叠，同页、同源及输出冲突会等待，其他命令作为串行边界。依赖上一项结果的工作放到下一批，不靠文件顺序表达依赖。发布加 `--no-open`，导航排序单独汇合。无依赖表单继续用专用 `create-form batch`。
- 独立分析、视觉设计、页面源码编写和验证任务，宿主有可用子 Agent 时使用委派。先确认本轮实际工具名、参数、允许的 Agent 类型与工具范围，以及是否支持同批并行调用或可回收结果的非阻塞派发。不能仅凭宿主名称、Agent 工具存在或后台 Shell 可用认定支持并行子 Agent。
- 委派时给出已确认需求与主题、输入文件、依赖、独占输出路径、真实应用/页面 ID、必要 Skill 指引及完成标准；不假设子 Agent 自动继承主会话的 Skill 或身份。两个任务分别写自己的文件。拿到真实任务句柄后主流程继续其他独立工作，在依赖汇合点回收并验证结果；只有阻塞委派且无并行工具调用时，按依赖顺序处理，不宣称加速。
- `cli_batch.available=false` 时通用 batch 不在当前受管范围内，使用已审计的命令族 batch；其他独立调用仅在宿主实际支持时并发，不换命令形式绕过门禁。子命令继续执行原有权限检查。
- 主流程负责共享配置、结果合并和导航排序。同一页面不并发修改/发布。`--stop-on-error` 只停止未启动任务，已经运行的任务会完成并返回结果；按每项 `success`、退出码和实际回读决定恢复，未知写入结果先查现状，不整批重试。CLI 结果按输入顺序返回，包含每项时间与实际并发峰值。


## Plan 的 CLI 交接

标准 Plan 首版采用一次收齐：业务任务完成一个 `business.json`，视觉直接复用 init 根据已确认选择生成的 `visual.json`，随后合并物化。这样首版只等待一次模型规划。品牌稿、参考图、页面级特殊视觉或明确的视觉精修要求命中时，才由视觉任务更新 `visual.json`；超大需求需要展示中间进展时才使用 [按模块更新方案](incremental-preview.md)，全部完成后再用 `materialize --from-preview` 汇总校验。

按 init 返回的 `authoring.pendingFields` 和 `context` 中的类型示例补齐事实，复核内容后设置片段 `ready=true`。init 返回的 `materialize.command` 是标准首版唯一生成命令。执行成功后直接展示 `outputs.html`，`revision` 仅用于内部确认绑定，用户可见文案统一称“当前方案”，不展示修订序号；不通过 `--from-preview`、preview、Glob 或额外 Read 探测产物；确认后不再物化或 patch。`explicitScope.allowInferredResources=false` 时，完整主题仍可作为 Plan 展示的一部分，但不进入应用设置、导航或发布执行。

`design-plan init` 返回 `parallelTasks` 和两个片段文件：

- `business.json`：init 已预填业务骨架，业务任务必须先读后写，保留 base；facts 只能填写 overview、dataModels、businessFlows、pages 和可选 execution，禁止加入 visualStyle。一次补齐所有普通表单的 sampleDataPlan（不造数写 skipReason）和所有自定义页面的 permissionSummary，完成后设 ready=true。可选 meta 仅填写 businessDomain、experienceTopology。
- `visual.json`：init 复用 `visualSelection`，将已选风格、主色和导航写入 facts.visualStyle。选择及所有自定义页的具体设计完整后，才设 `ready=true`；否则返回 `visual-design` 任务补设计细节；这不表示需要重选风格，PRD 完成后也不再比较候选或询问风格。按任务依赖读取业务页面，补齐 pageApplications；主题提供公共组件规则，不能代替逐页设计。

两个文件的 base 由 CLI 生成，保留原值；任务读取同一份需求、草稿和主题上下文。业务片段完成后保持稳定，变更时通知视觉任务重新核对页面设计。

主流程收齐结果后执行一次：

```bash
openyida design-plan materialize prd/<项目名>/build-plan.json \
  --business-file prd/<项目名>/business.json \
  --visual-file prd/<项目名>/visual.json --json
```

CLI 校验片段完成状态、来源版本、字段职责和页面对应关系，统一写入源计划、三份文档和主题 CSS。失败时保留原文件；合并成功后，后续修改使用当前计划的 patch 流程。

Fast 范围明确就创建/复用应用，独立准备主题；独立资源、主题配置和各页源码按真实工具能力并行，不派发 PRD/设计文档生成任务。Plan 使用同样的页面设计要求，按 CLI 返回的任务依赖填写片段后统一生成文件。

## 耗时记录

记录每项任务的开始、完成和等待时间。并行任务的总耗时按实际起止时间计算。CLI 的 timings 只记录本地生成阶段；模型规划与用户等待由宿主记录。

草稿按模块更新，正式产物在完整校验后一起保存。
